# 模式語言

**狀態：試行，不是律法**（2026-11-28）。本目錄沒有列入 `law/manifest.txt`，修改不需要修法紀錄與簽章。第一批模式用過一輪建構之後，再以修法列為律法（草稿 `docs/harness/53-pattern-language-inventory-draft.md` 的 M-2）。在那之前，本目錄與裁決、規格、架構規則衝突時，以它們為準。

## 一、這是什麼

論文（arXiv:2610.01372）把律法分成三樣：規格（要建什麼）、模式語言（依在地傳統怎麼建）、不適配清單（機器檢查什麼）。本目錄是第二樣。摘要見 `docs/harness/01-mgd-concepts.md`「四形式模式語言」與 `06-paper-digest.md` 3.4。

每個模式要有四種形式，缺一種就視為不存在：

| 形式 | 回答什麼 | 在本目錄的樣子 |
|---|---|---|
| 準則 | 什麼時候用、為什麼這樣寫 | `<模式>/doctrine.md` |
| 範本 | 正確的寫法長什麼樣子 | 會被編譯的 Java 檔（M-4）。**第一批還沒有**，從第一支建構的成品抽出（M-5） |
| 禁則 | 不得出現什麼、不得缺少什麼 | `<模式>/prohibitions.md` |
| 閘門 | 誰來判決 | 確定性的程式（ArchUnit 規則、範例執行器、比對器）。`prohibitions.md` 的每一條寫明有沒有閘門 |

只有閘門做判決。準則、範本、禁則是寫給建構者看的；沒有閘門的禁則，機器不會擋。

## 二、收什麼、不收什麼

只收本專案有約束、而且模型照預設寫法不一定會寫對的地方。通用的 Java、Spring 知識不寫。

## 三、檔案的格式

`doctrine.md`：

1. 適用範圍：什麼情況下用這個模式。
2. 寫法：逐點列出，每一點附出處（裁決編號或律法檔案）。
3. 為什麼。
4. 現況：程式現在符合的程度，數字怎麼來的。
5. 還沒有定的。

`prohibitions.md`：一張表，每一條有：

| 欄位 | 內容 |
|---|---|
| 編號 | `<模式縮寫>-P<n>` |
| 禁則 | 「不得…」。必須有的構造寫成「不得沒有…」 |
| 取代的寫法 | 它禁止的那個常見寫法 |
| 正本 | 這一條的權威出處。沒有裁決的寫「無，本目錄提出」 |
| 閘門 | 規則的編號；沒有就寫「無」 |
| 現況 | 現在有幾處不符 |

正本在別處的條文，這裡是重述。兩者不一致時以正本為準，並修正這裡。

## 四、目錄

| 模式 | 準則 | 範本 | 禁則 | 閘門 |
|---|:-:|:-:|:-:|---|
| `backend/command-use-case/` 命令 use case | ✓ | — | ✓ | 部分（ARCH-02、ARCH-03） |
| `backend/query-use-case/` 查詢 use case 與查詢埠 | ✓ | — | ✓ | 部分（ARCH-05 只管 `reporting`） |
| `backend/domain-event/` domain 事件 | 草稿 | — | 草稿 | 部分（範例的 `emits`）。依據的 D-098 尚未生效 |

三個模式目前都只有四種形式的兩種到三種，**照論文的定義都還不算存在**。

## 五、怎麼改

試行期間：一般的 PR。發現模式與程式不一致時，先分清楚是程式錯還是模式寫錯；模式寫錯就改模式，並在 PR 說明。

列為律法之後：照 `law/README.md` 的修法流程。
