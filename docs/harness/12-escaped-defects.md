# 漏網紀錄

依 `04-definition-of-enough.md` 第二節：每一個漏網的缺陷都要回應，回應方式是下列之一：

- 新增或修復偵測器。
- 修訂律法。
- 由負責人裁決「這類缺陷放在清單之外」，並指明改由什麼涵蓋。

「漏網」指閘門全部通過，缺陷卻是靠人工核對、審查或使用者才發現的。

### 立法時在未立法範圍找到的（不逐筆記）

2026-11-18 到 2026-11-26，後端問題側從 2 個 aggregate 立法到全部（D-066～D-089）。這段時間找到的缺陷，絕大多數是**立法一個切片之前**，用暫時的規格範例走真實的路徑實測，或讀程式對照權威文件找到的。

- 這些範圍當時在涵蓋清單裡是暫准：harness 明講「這裡沒有可執行的律法」（D-060），在那裡找到缺陷不是閘門失靈，所以不算漏網，也不逐筆記在這裡。
- 但數量不少：十幾個裁決、三十筆以上（沒有精確數）。例如 RANGE 的錯誤作答回 500、重複作答重複計分、理由含引號時稽核的 `detail` 是不合法的 JSON、重跑沒有院區檢查、案件的建立時間一律是 null。
- 每一筆的回應都是「修訂律法」：寫成待裁決的題目、裁決、規格與範例、建構。清單在各裁決的 Evidence 與對應的草稿（`16`～`44`），彙整在 `48-escaped-defects-inventory-draft.md` 第二節的 A 類。
- **這段時間最有效的偵測器是立法過程本身。** 這件事要留下紀錄，因為問題側現在已經全部立法，之後不會再有「立法時順便找到」的機會；之後的缺陷只會以漏網的形式出現。

## 之後怎麼記

負責人 2026-11-27 裁決（草稿 48 的 L-3、L-4）：

- **記什麼**：程式的缺陷，而且發現時相關的範圍已經立法、閘門是綠的。閘門本身的弱點記在 `03-harness-plan.md` 的驗證紀錄；流程的問題列進題目清單。
- **什麼時候記**：
  1. 起草的時候：草稿寫「查到的事實」時，每一個找到的缺陷都註明當時是否已立法。已立法的，在這份文件記一筆。
  2. 修缺陷的時候：建構 PR 的說明要回答「閘門為什麼沒擋到」。答案是「當時已立法」的，在這份文件記一筆。
- **每一筆都要有回應**（`04-definition-of-enough.md` 第二節）：新增或修復偵測器、修訂律法、或由負責人裁決放在清單之外。還沒有決定時寫「待裁決」，不留空白。
