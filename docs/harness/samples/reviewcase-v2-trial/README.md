# 第一輪：薄切片

**不是律法，也不是本專案的規格。** 這是用格式 v2 草案（`../../15-spec-format-v2-draft.md` 第四節第 4～8 項）試寫的 ReviewCase 規格，只用來檢驗 B 組的寫法夠不夠。它不改變 `law/coverage.txt`：ReviewCase 仍然是 `grandfathered`。

- 日期：2026-11-20。對照的程式是 `main` 的 `801c042`。
- 範圍：草案第七節指定的薄切片，也就是分派、初審提交、revision 歷程的讀取遮罩。
- 放在 `docs/` 底下，`spec_lint` 與執行器都不會讀到。
- **執行器沒有跑。** 下面說「寫得出來」，指的是語法上寫得出來、引用核對得過；範例會不會通過沒有驗證。

| 檔案 | 內容 |
|---|---|
| `round-1/review-case/model.yaml` | 3 條轉移、3 條不變量 |
| `round-1/review-case/usecases.yaml` | 4 支 use case：`AssignReviewCase`、`StartInitialReview`、`SubmitInitialReview`、`GetRevisionHistory` |
| `round-1/review-case/examples.yaml` | 19 個範例，矩陣展開後 26 個 |
| `round-1/review-case/OPEN-QUESTIONS.md` | 內容上待裁決的 3 題（權威文件與程式不一致） |
| `round-1/v2check_b.py` | 暫時的檢查，只核對第 4～8 項已定義的引用與結構 |

檔案裡的 `[缺口 B-xx]` 是第四節沒有定義、試寫時只能假設的寫法。編號用 B 開頭，和卡片試寫的 G-01～G-26 分開。


需要 PyYAML。

- 規則 30 條，其中 4 條 `proposed`。問題 0 個。
- 故意改壞 6 處（不存在的具名斷言、未宣告的事件、未定義的代碼、轉移沒有範例、矩陣欄數不符、不存在的 fixture），6 處都抓到。

## 缺口

一共 12 個，另有 4 個前提。

### 一、v2.0 修法前要先補進第四節的語法

| # | 缺口 | 影響 |
|---|---|---|
| B-01 | `absent` 的路徑、`expect.output` 的清單比對，都沒有定義怎麼穿過清單、怎麼只選某幾筆 | 歷程、提交清單、答案都是清單。盲審的規則是「初審那幾筆遮罩、本人複審那幾筆不遮罩」，不能選筆就寫不出來 |
| B-02 | `absent` 是黑名單，沒有「只有這些欄位」的斷言 | D-036 要求白名單不因新增欄位自動擴大；黑名單擋不住新增的敏感欄位。草案第五節寫「或封閉的輸出」，但第四節沒有語法 |
| B-03 | `then` 不能比對 `when` 自己的輸出 | 與卡片試寫的 G-08 相同。讀取遮罩的 `when` 就是那支查詢；提交初審的回應（`caseStatus`）也是要驗證的對象 |
| B-04 | 具名斷言只能放在 `observe`；矩陣不能代入 `then` 的 `result`、`code` | 與 G-10、G-11 相同。第 6 項自己的示範裡，`observe` 的那一步沒有 `run`，照字面無法執行 |
| B-05 | 矩陣展開的名稱 `名稱[甲,乙]` 含有 `[`、`,`、`]` | v1 規定範例名稱只能用英數字與 `_` `.` `-`，因為它是已知失敗清單裡的身分 |
| B-06 | 型別詞彙沒有時間 | `dueAt`、`updatedAt`、`submittedAt` 都宣告不了 |
| B-07 | 時間值怎麼比對沒有定義；目錄層級的預設時鐘寫在哪裡也沒有定義 | 程式同時有帶時區與不帶時區的時間。期望值寫成字串時，依哪個時區換算要先講清楚，否則同一個範例在不同機器上結果不同 |
| B-08 | 事件：規格的事件名稱怎麼對到程式、`with` 比對事件的哪些欄位、被拒絕時「沒有事件」怎麼寫，都沒有定義 | use case 有「`X` 對到 `XUseCase`」的慣例，事件沒有。domain-events §2 第 3 點（非法轉移不得發布事件）目前寫不成斷言 |

### 二、薄切片與既有檢查互相卡住

| # | 缺口 | 影響 |
|---|---|---|
| B-09 | 轉移沒有條件欄位；`by` 必須在同目錄；第 8 項要求每條轉移都有範例 | state-machine §3.2 的 16 列只寫得進 3 列。固定初審依分數走到兩個不同的狀態，也寫不出來。結果是：**薄切片立法時，狀態機一定是不完整的**，而格式沒有辦法標示「這些轉移存在、但還沒立法」（`deferred_behaviors` 只是文字） |
| B-10 | 一個目錄只能有一個狀態列舉的轉移；fixture 不能跨目錄引用 | 提交（ReviewSubmission）有自己的狀態機，但改變它的 use case 和 ReviewCase 是同一批。草案第一節把「跨 aggregate」列為 B 組的需求，第四節卻沒有對應的項目。另外，「啟用中的專案」這 7 個準備步驟要從 review-project 整份抄過來 |
| B-11 | `save` 只能取輸出的同名屬性，取不到清單裡的值 | 案件的 id 只能從「列出這個批次的案件」取得第一筆 |
| B-12 | 查詢的 `output.fields` 只有一份，每一項只有名稱與型別 | 清單元素有哪些欄位沒有地方定義；「這個欄位只有某些角色拿得到」也寫不出來。讀取遮罩的規則只能寫在 `text`，不是結構 |

### 三、前提（不是格式的缺口，但會擋住薄切片）

| # | 前提 | 說明 |
|---|---|---|
| P-1 | **薄切片的準備步驟需要 7 支還沒立法的 use case** | 案件只能由抽選建立，所以每個範例都要先跑 `ExecuteSampling`、`ListReviewCases`；遮罩的範例還要 `SaveInitialReviewDraft`、`FixInitialReview`、`AssignRereviewer`、`StartRereview`，觀察要 `GetReviewCaseDetail`。照 v1 的規則，`needs` 未滿足的範例算未通過。**所以薄切片單獨立法，26 個範例有 25 個會是紅的。** 抽選的候選來自外部（`CandidateSourcePort`），照草案的原則應該是 C 組第 9 項的埠；目前靠開發用的替身固定回 5 筆 |
| P-2 | 程式的參數名稱對不上規格 | `ListReviewCases` 收一個 `criteria` 物件，`AssignRereviewer`、`StartRereview` 收一個 `cmd` 物件。執行器依參數名稱對輸入，所以規格要寫 `input: { cmd: {...} }`，這是實作詞彙。要由建構 PR 把參數攤平 |
| P-3 | 逾期沒有可以立法的規則 | 草案第五節把「指派期限、逾期」列為時鐘的用途。但 `api-spec.md` §10.3 明說期限的檢核尚未定稿，輸出也沒有表示逾期的欄位。時鐘在薄切片裡只用得到 `updatedAt` 與 `submittedAt` |
| P-4 | 查詢會改變狀態 | 准許完整讀取時會記下讀取者（D-055 第 5 點），影響之後能不能指派。範例寫得出來，但「`observe` 只跑查詢」不再等於「`observe` 不改變狀態」：在 `observe` 裡用管理者讀一次，就會讓那位管理者不能被指派為複審 |

### 和卡片試寫重複的缺口

B-03、B-04 與 G-08、G-10、G-11 是同一件事。卡片試寫把它們歸在 v2.1（C 組）要補的語法，但 B 組的第一個使用者就會撞上，所以要提前到 v2.0。

## 試寫查到的內容問題

寫規則時要逐條找出處，才會碰到這三題。詳見 `round-1/review-case/OPEN-QUESTIONS.md`（第二輪增為 5 題，見 `round-2/OPEN-QUESTIONS.md`）：

1. 6 個錯誤代碼，`api-spec.md` §4.2 寫的和程式用的不一樣，或權威文件根本沒有。
2. 指派時沒有給初審醫師或期限，權威文件沒有寫代碼，程式也沒有一致的行為。
3. `domain-events.md` 說提交初審要發出 `InitialReviewCompleted`，程式沒有發。

這些和漏網紀錄 E-01 是同一類：缺陷落在沒有可執行律法的地方。
