# 報表的日期篩選固定以台北解讀

狀態：**已裁決**（2026-11-24）。負責人對 V-1～V-5 全部照建議裁決（V-4 的時區用 `UTC`），條文是 `decision-log.md` 的 D-077，以那裡為準。本文件不是律法，下面保留起草時的版本（main = `a18fbb7`）。題號 V-1～V-5 只在本文件使用。

## 一、背景

- 題目清單待辦第 1 項。負責人 2026-11-23 決定：報表匯出頁（UI-017）與儀表板（UI-015）的起日、迄日固定以 `Asia/Taipei` 解讀，不依瀏覽器的時區。
- 憲法草案第一條第 4 點：只有日期、沒有時刻的值（`YYYY-MM-DD`）必須由裁決明文指定，並寫明以哪個時區解讀。
- 這兩頁的起日、迄日正是這種值，但**沒有任何裁決指定時區**。D-057 只定了 API 的 `from`、`to`（含起不含迄、必填、`from` 早於 `to`），沒有提到畫面的日期怎麼換算。「瀏覽器的本地時區」只寫在 UI 文件裡。本題是補上缺的裁決，不是修改既有裁決。

## 二、查到的事實

**後端（不用改）**
- `ReportController` 的 `from`、`to` 已經是 `Instant`。儀表板（選填）與匯出（必填）都以 `from ≤ createdAt < to` 過濾，`createdAt` 是 `Instant`。
- `reporting/` 與 `ReportController.java` 在 `law/coverage.txt` 是 `grandfathered`。本題不動後端，D-060 不受影響。
- `specs/` 沒有報表的規格，沒有範例要改。

**前端（`features/reports/report-export/export-date-range.ts`，兩頁共用）**

| 函式 | 現況 | 問題 |
|---|---|---|
| `toExportRange` | `new Date(y, m, d)` 取瀏覽器本地的 00:00，再 `toISOString()` | 瀏覽器不在 UTC+8 時，查詢範圍偏移 |
| `previousFullMonth(new Date())` | 以瀏覽器本地的「今天」算上一個整月 | 跨月的那幾個小時，預設區間可能錯一個月 |
| `isOrderedRange` | 只比較兩個日曆日期的先後 | 與時區無關，不用改 |

- `shared/time/taipei-time.ts` 已有 `TAIPEI_OFFSET = '+08:00'`（D-075 第 5 點）。台北沒有日光節約時間，固定位移是安全的。

**文件**
- UI-017 §4（第 104～105 行）：「日期欄位是使用者瀏覽器所在時區的日期；院內環境為 Asia/Taipei」「起日 00:00（本地）」。§驗收第 1 項（第 152 行）也寫「（本地）」。

- UI-017 第 106 行的例子（`from=2026-09-30T16:00:00Z`、`to=2026-10-31T16:00:00Z`）本來就是台北的結果，不用改。
- UI-017 第 124 行：CSV 檔名的日期是「畫面上的本地日期」。

**測試**
- 單元測試 `export-date-range.spec.ts` 的預期值也用 `new Date(...)` 算，因此在任何時區都會通過，**測不出時區問題**。
- e2e（`ui015-…`、`ui017-…`）寫死台北的結果（`T16:00:00.000Z`），但 Karma 與 Playwright 都沒有設定時區，只有在 UTC+8 的機器上才會通過。

**順帶發現**
- `report-export.service.ts` 第 67 行的註解說 `closedAt` 是「不帶時區的伺服器本地時間（後端 LocalDateTime）」。D-075 之後後端是 `Instant`，註解過時。

## 三、V-1：日期欄位的意義與送出轉換

### 建議

- 起日、迄日是 `Asia/Taipei` 的日曆日期，不依瀏覽器的時區。
- `from` ＝ 起日 00:00 `+08:00`；`to` ＝ 迄日**次日** 00:00 `+08:00`。兩者以 UTC（`Z`）送出，維持 D-057 的含起不含迄，畫面上的迄日含當天。
- 例：起日 2026-10-01、迄日 2026-10-31 → `from=2026-09-30T16:00:00Z`、`to=2026-10-31T16:00:00Z`（與現在 UI-017 的例子相同）。
- 換算的位置（憲法第一條第 3 點）：前端的 `export-date-range.ts`。後端只收時間點，不做日期換算。

### 選項

- **A（建議）**：如上，前端換算。
- **B**：API 改收 `startDate`、`endDate`（`YYYY-MM-DD`），由後端以台北換算。要改 HTTP 契約與 grandfathered 的 `reporting`，範圍大得多。
