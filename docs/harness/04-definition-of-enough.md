# 怎麼判斷 harness 做得夠不夠

## 論文的答案

理論篇附錄 A 直接定義了「足夠」：

> 充分性是相對於主張的。harness 足夠的條件不是它建立了絕對的正確性，而是它履行了支持那個有界主張所需的每一項義務，包括證明清單上的每一項都真的被評估了。

拆開來是三件事：

1. **主張是有界的。** harness 能說的只有「在這份律法之下，清單上的每一項不適配都不存在」。清單以外的事，它什麼都沒說。
2. **十條義務都有機制履行。** 對照表在 `03-harness-plan.md` 第三節。
3. **清單上的每一項都真的跑了。** 被跳過的閘門不算通過；掃描範圍是空的檢查不算通過；報告要列出沒被評估的項目數。

所以「夠不夠」要換成兩個問題來問：我想主張什麼？支持這個主張的義務都履行了嗎？

清單本身永遠不會完成。論文的處理方式是把清單當成受治理、持續成長的產物：每個漏網的缺陷都要有回應（見第二節）。

以下第一、三、四節是本專案的操作化建議，不是論文的內容。

## 一、及格線：四項測試全過

親手做這四件事。全過就是最小可用，可以開始讓 AI 在上面工作。任何一項沒過，就還不夠。

| # | 做什麼 | 必須發生什麼 | 對應義務 |
|---|---|---|---|
| 1 | 手寫違規：在 `interfaces` 層直接呼叫 `infrastructure` 的類別，發 PR | CI 紅燈 | P1 |
| 2 | 改 law：在一個 PR 裡修改 `decision-log.md` 或規則檔 | 沒有指定的人核准就無法合併 | P6 |
| 3 | 弄壞偵測器：把一條 ArchUnit 規則改成永遠通過 | 違規樣本的測試失敗 | P2 |
| 4 | 改需求：在 spec 加一條規則和一個驗收範例，不改程式 | 驗收紅燈，直到程式補上 | P10 |

以現況來說，前三項一兩天可以做完。第 4 項最難，因為驗收範例目前只是 YAML，還不能執行。

這四項改編自參考 repo 的 `.dev/course/exercise-mgd-quickstart.md`。原教材的四個觀察點是：AI 依 spec 產生程式並自己修到通過、手動違規被 gate 擋下、AI 想改規則被擋下、人改需求後新規則傳到程式和測試。

## 二、持續的指標：漏網率

及格之後不再問「夠不夠」，改成記錄兩個數字。

- **植入測試**：每隔一段時間故意放進 10 個不同類型的錯，看 gate 擋下幾個。類型例如分層違規、漏掉前置條件、測試沒有斷言、跨院區讀取。這個數字就是 harness 目前的能力。
- **實際漏網**：每次 code review、測試人員或上線後發現的錯，問一句「這個 gate 為什麼沒擋到」，記成一筆。

論文對漏網缺陷的要求比「記一筆」嚴格：**每一個**都必須用下列方式之一回應，不是等到第二次。

| 回應方式 | 適用情況 |
|---|---|
| 新增偵測器，或修復既有的偵測器、它的掃描範圍、它讀取的文件 | 律法已經寫了這項期望，是偵測出了問題 |
| 修訂律法 | 律法漏寫，或世界出現了新的要求 |
| 人類明確裁決：這類缺陷放在清單之外，並指明改由什麼來涵蓋 | 沒辦法做成確定性的檢查 |

第三種回應很重要：它讓「機器沒檢查這一類」成為一筆有紀錄的決定，而不是沒人知道的空白。建議在本目錄維護一份漏網紀錄，每筆寫明缺陷、回應方式、對應的規則或裁決。

論文也要求一組不交給建構者的獨立測試，用來回答「閘門全過時，行為對不對」。沒有這一組，漏網只能等人或使用者發現。

## 三、每個機制都要有證據

義務對照表上的每個機制，都要能指出檔案，並且有一次「它真的擋下東西」的紀錄。寫不出證據的那一列標 ⚠️，照實留著。參考 repo 的 ezgo 自己也有四列 ⚠️。

每條 gate 寫明它擋什麼、不擋什麼。

## 四、該停手的訊號

這一節是實務建議，論文沒有給停手的準則。論文只說建立和維護的成本沒有量測，而且只由人類核准規則可能形成瓶頸。

新增規則前先檢查：

- 它對應哪一次實際發生的錯，或律法的哪一條？論文要求新閘門以律法為依據。
- 誤報率低嗎？論文要求新閘門的誤報率要低。誤報要修閘門，不能改程式去遷就。

不要用的理由：

- 「這條規則很久沒觸發了」不是移除它的理由。論文明說守護在地慣例的規則不因統計上的安靜而退役，只有傳統或架構改變、它檢查的情境不存在時才退役。

哪些東西不值得納入：論文指出探索性原型、一次性工具、架構還在摸索的部分，這套做法買到的很少。它的參考實作只治理後端，前端沒有納入。

正面例子：參考 repo 的 57 條規則每一條都指回一個出處。
反面例子：`ezgo-law-guard.py` 長到 1696 行，仍然只能做到事後發現。

## 五、harness 擋不住的，要另外處理

| 類別 | 處理方式 |
|---|---|
| spec 對不對 | 人審，加上只透過 use case 的驗收範例 |
| 語意與安全（授權、併發、交易邊界） | 人審或專門的測試，例如「別院被拒」的測試 |
| 測試沒有斷言、什麼都沒驗 | mutation testing 抓得到這一種 |
| 測試驗的是錯的業務規則 | mutation testing **抓不到**：它衡量的是測試與程式的關係，不是測試與規格的關係。論文提的三個方向：把規格裡每個預期值追到測試的斷言；改動規格的一個預期值後測試應該變紅；由驗收範例直接機械產生測試 |
| 驗收例子比規則窄 | 人審時對照規則的範圍；論文的案例是規則寫「空白字元」，例子只用了空字串 |
| 驗收範例被跳過 | 把「跳過」算成未通過；`spec-draft` 已經這樣定義 |
| 律法自己互相矛盾 | 人審；每次矛盾造成漏網後，補一道核對的檢查 |

「由驗收範例直接機械產生測試」對本專案特別有意義：如果 `examples.yaml` 由一支確定性的執行器直接跑，而不是讓 AI 把每個範例翻成測試程式，S–T 這一環就從「生成後大致檢查」變成「機械推導」。代價是執行器本身要被驗證。
