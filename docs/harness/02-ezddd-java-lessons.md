# ezddd-java 的教訓與能力限制

依據是參考 repo 的文件：`.claude/skills/ezgo/references/mgd-obligations.md`、`.dev/course/`、`.dev/lessons/`、`.claude/skills/ezddd-java/references/uc-executor/uc-workflow.md`、兩份 gate 規則檔。

查證範圍的限制：

- 沒有實際執行過 `/execute-uc` 或 `/execute-go-uc`。
- 51 份 ADR 沒有逐份讀。
- `FAILURE-CASES.md` 等幾份 lessons 只看了標題。
- hook 腳本沒有逐行讀，流程是從教材的流程圖得知。

## 先分清楚兩個東西

本文件第一至四節講的是**參考 repo 裡的課程版 harness**，不是論文的參考實作。兩者規模差很多：

| | 論文的 Java 參考實作（未公開） | 參考 repo 的課程版 |
|---|---|---|
| 確定性規則 | 188 條 | 57 條 |
| 阻擋性閘門 | 28 道，分五類 | Gate 1 與 Gate 2.5 為主 |
| 規格格式 | 依問題框架分類的 YAML，有 39 條規則的 linter | JSON，沒看到 linter |
| 測試是否涵蓋規格 | 18 道結構閘門做確定性比對 | LLM 自行檢查，文件寫 best-effort |

所以第二節列的限制，有些是課程版特有的（例如「測試涵蓋由 LLM 自己檢查」），不能直接算在 MGD 頭上。論文自己承認的限制見 `01-mgd-concepts.md` 最後一節，以及本文件第五節。

兩者的關係是從規模數字推斷的，沒有向作者確認。

## 一、踩過的坑

| 坑 | 說明 | 對本專案的啟示 |
|---|---|---|
| 寫了「強制」不等於強制 | 專案 2024 年就在累積教訓，文件結尾寫「我承諾」；確定性的 Gate 2.5 到 2026-03 才出現 | 規則要能讓 build 失敗，否則只是建議 |
| LLM 審自己的程式會審錯 | 記錄過它對自己寫的違規給了通過，也曾給有問題的檔案五星 | 不拿 LLM 的審查當 gate |
| 由 LLM 呼叫的 gate 會被跳過 | 所以才有 Stop hook、marker、checksum；而且 Stop hook 不涵蓋 sub-agent | gate 放進 CI，不靠 AI 自己記得跑 |
| gate 自己會壞 | 一條規則曾與 workflow 的選項矛盾，該模式永遠過不了；自測腳本也出過誤報 | gate 也要有測試 |
| template 會被逐字照抄 | 範本裡一個型別錯誤，會出現在每一支 use case | 範本要先被 gate 驗過 |
| 規則重複寫在多處 | 結果是 1031 行的權威登記表加 538 行的同步檢查腳本，整個 skill 約 3.4 萬行 | 每條規則只寫一處 |
| spec 用陣列位置引用規則 | 例如 `constructorPreconditions[0]`，插入一條就全部位移 | 用穩定的規則編號；`spec-draft` 已經這樣做 |
| spec 沒寫清楚，實作各自決定 | create-pbi 的 `estimateType`：Java 接受、Go 拒絕 | 修的順序是人裁決、寫回 spec、加驗收範例、最後才改程式 |
| law guard 的軍備競賽 | `ezgo-law-guard.py` 長到 1696 行、404 個測試案例，結論仍是只能事後發現 | 用 PR 審查當邊界，不要複製這支腳本 |
| 框架專屬的坑佔大半 | 十大規則和 lessons 多數是 ezddd 元件的陷阱 | 不繼承就不會踩到；但合規有一部分來自框架基底類別，要用範本和 gate 補回來 |
| 文件會被照字面執行 | Go 跑了 11 輪、Java 9 輪模擬學員，每輪都找到教材錯誤 | 驗證 harness 本身要留預算 |

## 二、它不是萬無一失

ezddd-java 保證的是「產出符合專案慣例」，不是「產出是對的」。它自己的文件也沒有宣稱萬無一失。

### 真正被強制的只有兩樣

- Gate 1：測試通過。
- Gate 2.5：57 條文字規則（regex 掃原始碼）。

### 連「spec、程式、測試一致」也只是盡力而為

**測試有沒有涵蓋 spec**

- Java 版由 LLM 自己檢查。`uc-workflow.md` 原文寫「best-effort」，以及「Traceability verification is not part of this workflow」。
- Go 版的 GS-05 只檢查測試檔裡有沒有 `// spec: …[i]` 這種註解，不檢查那個測試是否真的驗了那條規則。
- GS-05 只看當次指定的那一份 spec。

**測試能不能證明程式**

- 測試和程式出自同一次生成，對 spec 的理解錯了會兩邊一起錯。
- 記錄過「丟例外算過，否則檢查 FAILURE」的測試寫法，兩種結果都通過。
- 沒有東西檢查測試的強度。mutation testing 是獨立模組，不在主流程的 gate 裡。

**程式有沒有做到 spec**

- Gate 2.5 不看 spec 內容，只看寫法慣例。
- 黑箱驗收（Gate GA）是唯一獨立的尺，但有三個條件：
  - spec 沒有附驗收檔就不擋，文件寫「it is not a failure」。
  - 用到尚未產生的 use case 就跳過。A/B 實驗中 create-product 是 0/3，全部跳過。
  - 只能驗透過 use case 看得到的行為。事件內容、稽核紀錄、非同步時序看不到。
- spec 模糊時，兩種實作都算一致。`estimateType` 的差異是比對兩個 binding 才發現的；只有一個 binding 時不會有人發現。
- spec 有、程式刻意不做的部分（`IGNORE`、`UNUSED_INPUT`）只是回報給人。

### 強制力的洞

| 洞 | 出處 |
|---|---|
| Stop hook 不涵蓋 sub-agent | A/B 實驗的限制一節 |
| 沒有 CI；其他工具或人手改的程式不受約束 | 參考 repo 沒有 CI 設定 |
| 修正期間「不得改規則」沒有 hook 強制 | `mgd-obligations.md` P4 |
| law 保護只能事後發現；同一個 OS 使用者可以連基線一起改 | `mgd-obligations.md` P6 |
| 翻譯表與 spec 之間沒有自動對帳 | `mgd-obligations.md` P10 |
| 幾條禁令標成 `review only`，等於只是建議 | `mgd-obligations.md` P3 |

### 適用範圍的限制

- 只做從零生成，沒有處理既有程式碼的機制。
- 規則綁死框架，框架升級時 harness 要跟著改。
- spec 帶實作詞彙，換技術就得寫翻譯表（ezgo 那份有 828 行）。
- 不涵蓋前端、資料庫遷移、部署、非功能需求。
- 併發、交易邊界、效能、授權邏輯都不在文字規則的範圍內。

### 人仍然是瓶頸

harness 自動化的是「寫程式」，不是「決定寫什麼」。本專案一個 aggregate 的 6 支 use case，就需要人裁決三十幾題。

## 三、為什麼規則會變成窮舉

兩邊的 gate 規則其實是同一種東西：固定的 regex 清單（Java 57 條、Go 34 條）。窮舉出現在別處。

- **Java 規則看起來固定**，是因為框架把寫法收窄了：抓的多半是只有一種拼法的 import 或註解。但固定不代表沒漏，例如 F-01 的 pattern 是 `^\s*@(Service|Component)\s*$`，寫成 `@Service("x")` 就不會命中。
- **Go 沒有框架**，同一個違規有多種拼法，所以 regex 要列多種寫法。
- **law guard 是真正的窮舉**：它要從 Bash 指令的文字判斷會不會改到 law，而 shell 有太多方式做同一件事。

根本原因：misfit 定義在結果上（例如「handler 碰了資料庫」），窮舉發生在偵測器改看手段的時候。law guard 後來的兩個修正都是放棄窮舉：改成白名單，以及加一層 checksum 直接比對結果。

對本專案的結論：盡量讓 gate 直接看結果。

- 架構規則用 ArchUnit，它看的是編譯後的依賴關係，一條規則涵蓋所有寫法。
- law 保護交給 CODEOWNERS、branch protection 和 CI，它們看的是 diff 的結果。
- regex 只留給真的只有一種拼法的東西。

## 四、值得學的

- **每條規則都指回一個實際發生過的錯**（`authority_ref`）。規則清單是從漏網的案例長出來的，不是事先設計完的。
- **每條規則配一個違規樣本**（ezgo 的 `fixtures/mutations.txt`），證明規則真的會響。檔頭寫著「a rule without a fixture is a rule that is not known to work」。
- **把缺口照實列出來**。`mgd-obligations.md` 十列裡有四列標 ⚠️，並附已知缺口清單。
- **黑箱驗收格式**（`.dev/specs/ACCEPTANCE-FORMAT.md`）：只透過 use case 的 `run`、`input`、`then`、`observe`，不含框架詞彙。
- **完成報告固定列出交給人判斷的項目**（SPEC_GAP、UNUSED_INPUT 等）。
- **A/B 實驗**：有 gate 的一組 14/14 合規，沒有的一組 9/14。它只衡量是否遵循慣例，不衡量程式品質。

## 五、論文記錄的失敗案例

出自 `references/` 的綜述篇。每一則都對應一條義務，也都是本專案會遇到的情況。

| 發生了什麼 | 對應義務 | 之後的對策 |
|---|---|---|
| 提示詞和範例不論寫了多少規則，都沒有可靠地防止違規一再出現 | P2、P3 | 加入確定性閘門 |
| 建構者把一份 80 行的規格刪成 12 行，30 道閘門因此過了 28 道 | P4 | 規格在執行期間一律凍結 |
| 建構者修使用案例 A 時弄壞了 B，接著改寫 B 的測試去接受這個錯誤 | P5 | 防護機制還原所有超出修補範圍的修改；A 若需要動 B，交給人決定 |
| 建構者判斷某道閘門誤判了正確的程式，它沒有改壞程式去遷就，而是提出詢問 | P6、P8 | 人類修正了閘門 |
| 一道閘門悄悄跳過了 62 個驗收場景，因為測試放在它不搜尋的目錄 | P10 | 修好後立刻找到兩個漏掉必要檢查的測試 |
| 規則說「只有空白字元視同省略」，驗收情境的例子用的卻是空字串。程式只處理了空字串，測試通過，每道閘門都過 | P2、P10 | 這是「見證比規則窄」：例子沒有涵蓋規則的全部範圍 |
| 一條規則禁止修改共用設定，另一條允許用固定值當退路，而需求排除固定值。建構者兩條都遵守，閘門全過，185 個端對端測試只過 79 個 | P6、P8 | 缺陷在律法本身。人類裁決後修訂律法，再加一道新閘門 |
| 另外兩個模型用防護沒檢查到的 shell 指令改了設定，通過全部 185 個測試 | P6 | 通過行為測試不代表遵守規則 |
| 能力強的建構者沒犯下 harness 偵測不到的錯，harness 的弱點因此沒有顯露 | P9 | 換較弱的模型才暴露出來 |

對本專案的三個提醒：

- 驗收例子要對照規則的範圍來寫，不是有一個例子就算涵蓋。
- 律法自己會互相矛盾，而且起點是人寫的規則。
- 需要一組**不交給建構者**的獨立測試，才知道閘門全過時行為對不對。論文用的是 185 個端對端測試和 1,323 筆 HTTP 請求的比對。
