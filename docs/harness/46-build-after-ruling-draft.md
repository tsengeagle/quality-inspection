# 建構不得先於它依據的裁決併入主線

狀態：**草稿，待裁決**（2026-11-26 起草，main = `5d1f462`）。本文件不是律法；題號 B-1～B-8 只在本文件使用。

題目清單待辦第 1 題（負責人 2026-11-26 列入，排在最前）。

## 一、問題

修法機制擋住了「沒有簽章的律法修改」，但沒有擋住「依據還沒生效的裁決所做的建構」。

`law-check` 對一個 PR 只問兩件事：它有沒有改律法路徑；它改的問題側檔案在不在涵蓋清單裡。兩者都沒問題時，分類為建構 PR 而通過。它不問這個建構依據哪一個裁決，也不問那個裁決進了 `decision-log.md` 沒有。

所以下面這件事目前做得到：裁決的修法 PR 還在等簽章，依據它的建構 PR 已經併進 `main`。之後修法 PR 若被退回或改了內容，`main` 上就有一段沒有律法依據的程式。

## 二、查到的事實

**讀程式、文件與 git 歷史，加上本機執行 `law_check.py`。** 沒有在 GitHub 上實測新的規則（還沒有寫）。

### 發現的經過

1. D-096 的修法 PR #194 在等簽章時，負責人同意先做建構（#195：`ScoreSheetController` 的回傳型別，行為不變），條件是「不能先於修法併回主線」。
2. #195 的分支刻意疊在 #194 的分支上，本機的判決：

   | 情境 | 指令 | 判決 |
   |---|---|---|
   | #194 未合併，#195 對 `main` | `law_check.py --base origin/main --head HEAD` | 未通過：分類為修法 PR；夾帶程式、沒有核准簽章 |
   | 模擬 #194 合併後 | `law_check.py --base e7cd58c --head HEAD` | 通過：分類為建構 PR |

3. 同樣的修改如果從 `main` 開分支，差異裡沒有律法路徑，`law-check` 會判為建構 PR 而通過。這一點是從判決程式的邏輯讀出來的（事實 4），**沒有另外開 PR 實測**。

### 判決程式的現況

4. `harness-core/law_check.py`（0.8.0）的 `evaluate_with_reminders`：以 `merge-base(base, head)` 到 `head` 的差異分類檔案。沒有律法修改、沒有修法紀錄、沒有核准檔時，分類為建構 PR，只做涵蓋清單的檢查（D-060）。
5. 判決程式只讀檔案的差異，不讀提交訊息、PR 的標題或說明。
6. 判決程式已經有「裁決存在」的比對：修法紀錄的 `decision` 欄位用 `^#+\s*D-nnn\b` 去找 `decision-log.md` 的標題（讀的是 head，因為裁決可以在同一個修法 PR 裡新增）。
7. CI 用 `pull_request_target`，判決程式與清冊取自 base；觸發的事件包含 `edited`（改 PR 的標題或說明會重跑）。
8. 本 repo 只允許 merge commit（`07-github-settings.md`），所以 PR 裡每一個提交的訊息都會原樣進到 `main` 的歷史。

### 現有的慣例

9. 本機看得到的 `main` 歷史是 147 個提交（淺層複製，不是完整歷史）。其中非 merge 的 `build` 提交 25 個：
   - 24 個的標題帶裁決編號，例如 `build: D-095 逾期看目前階段的期限`。
   - 1 個沒有：`build: 刪除沒有使用的 CloseWithoutRereviewRequest、SendToRereviewRequest`。這是沒有對應裁決的清理。
10. 回溯檢查：這 24 個提交標題裡的每一個裁決編號，在該提交自己的 `decision-log.md` 裡都找得到（用 `git show <提交>:docs/01-requirements/decision-log.md` 比對 `^## D-nnn `）。也就是在看得到的歷史裡，**沒有發生過建構先於裁決**，靠的是順序紀律。
11. 這個回溯檢查比對的是提交當下的檔案，不是當時 `main` 上的檔案；兩者在「建構分支有沒有包含修法」這一點上可能不同。更嚴格的回溯沒有做。
12. `decision-log.md` 有 95 個裁決。`### Status` 之後的寫法：89 個是 `` `accepted` ``，3 個是 `` `superseded` ``，D-013～D-016 這 4 個的寫法不同（起草時沒有逐一看）。

### 義務的對應

13. 這個缺口對應 MGD 的 P4（每次修復期間，凍結評判修復的依據）與 P6（建構者不得自行修訂律法）。現在的機制做到了「建構 PR 不能改律法」，沒有做到「建構 PR 依據的律法已經定案」。`03-harness-plan.md` 第三節的義務對照表對 P4 的現況沒有記這一點。

| 情況 | 現在擋得到嗎 | 靠什麼 |
|---|---|---|
| 建構需要新的規格範例才會綠 | 擋得到 | 範例在 `specs/`，要簽章 |
| 建構要解凍 `known-test-failures.txt` 的項目 | 擋得到 | 清單裡要先有那一行，新增行要簽章 |
| 建構新增問題側的檔案 | 擋得到 | 要先登記進 `coverage.txt`，要簽章 |
| 建構改了 HTTP 的回應形狀 | 擋得到 | `http.yaml` 是封閉的契約，要簽章 |
| **建構行為不變，依據待簽的裁決**（例如 #195） | **擋不到** | — |

第二個擋不到的情況（沒有範例涵蓋的行為變更）是範例涵蓋度的問題，不是順序的問題；本題的機制對它只有間接的效果（要求建構說出依據），不在本題解決。

## 四、待裁決

### B-1　要不要用閘門擋

| 選項 | 作法 |
|---|---|
| A | 不擋。把「修法在前、建構在後」寫成給 AI 的指示（傳統），維持順序紀律 |
| **B（建議）** | 建構 PR 必須宣告它依據的裁決，`law-check` 檢查宣告的裁決已經在 **base** 的 `decision-log.md` 裡 |
| C | 不靠宣告，由修法紀錄列出「之後的建構會改哪些檔案」，`law-check` 反過來比對 |

B 的理由：

- 這個 harness 的原則是「遵循看得到，內化無法驗證」（P9）。看得到的歷史裡沒有出過事（事實 10），但那是紀律，不是閘門。
- 檢查的材料都在 git 裡，判決程式已經有比對裁決編號的程式（事實 6），新增的邏輯很少。
- 讀 base 是關鍵：修法 PR 還沒合併時，它新增的裁決不在 base，所以依據它的建構 PR 過不了。合併之後自動放行。

C 的問題：修法時通常還不知道建構會改哪些檔案，寫了也很快過時。

B 擋不住的：宣告了錯的裁決（例如隨便填一個已存在的編號），或把有依據的建構宣告成「沒有裁決」。它擋的是**誠實但搶先**，不是惡意。這與修法機制本身的定位一致（`law/README.md`：「機制只管程序，不判斷修改本身合不合理」）。

### B-2　宣告寫在哪裡

| 選項 | 作法 | 優點 | 缺點 |
|---|---|---|---|
| **A（建議）** | 提交訊息 | 在 git 裡，不分平台（GitHub、GitLab 都一樣）；merge commit 會把它帶進 `main` 的歷史；本機就能跑 | 寫錯要改提交 |
| B | PR 的標題或說明 | 好改 | 只在平台上；本機跑不了；合併後可以再改，歷史不可靠 |
| C | 分支名稱 | 不用多寫 | 一個分支只能表達一個裁決；本 session 這類被指定分支名稱的環境做不到 |

A 之下的寫法，建議沿用現有的慣例（事實 9）而不是發明新的欄位：

- 提交的**標題**裡出現的每一個 `D-nnn`，都算宣告。
- 標題沒有任何 `D-nnn` 時，提交訊息必須有一行 `Ruling: none`，後面寫理由（見 B-3）。

這樣 25 個既有的 `build` 提交裡 24 個不用改任何習慣。

### B-3　沒有對應裁決的建構

純重構、清理、修缺陷、升級相依套件，沒有裁決可以指。

| 選項 | 作法 |
|---|---|
| **A（建議）** | 允許。提交訊息寫 `Ruling: none — <理由>`；`law-check` 通過，但在報告列為提醒（與暫准範圍的提醒相同，GitHub 上顯示為 warning） |
| B | 不允許。動到問題側的修改一律要有裁決 |
| C | 允許，而且不需要寫理由 |

A 的理由：B 會讓每一個小清理都要先修法、等簽章，成本太高，結果是大家硬湊一個編號。C 讓 `none` 變成沒有成本的預設值。A 讓「沒有依據」這件事被看見，由負責人在合併前判斷。

修缺陷值得另外說：缺陷的定義是「程式不符合既有的規格」，所以它有依據，應該宣告那條規則所在的裁決，不是 `none`。這一點建議寫進給 AI 的指示，閘門不判斷。

### B-4　哪些 PR 要宣告

| 選項 | 範圍 |
|---|---|
| **A（建議）** | 差異裡有「非律法、也不是文件」的檔案的 PR。判決程式已經算出這份清單（`program`） |
| B | 只有動到問題側（`coverage.txt` 的 `@problem-side`）的 PR |
| C | 所有建構 PR，包含只改文件的 |

A 的理由：前端、`infrastructure`、測試都不在後端的問題側清單裡，但它們的修改同樣可能依據待簽的裁決（例如前端移除欄位，#192）。只改 `docs/` 與 `.md` 的 PR（草稿、題目清單）不需要宣告。

哪些提交要看：PR 範圍內（`merge-base..head`）的非 merge 提交。只要求「改到 `program` 檔案的提交」要有宣告，或要求「每一個提交」，見 B-5。

### B-5　以提交為單位，還是以 PR 為單位

| 選項 | 作法 |
|---|---|
| **A（建議）** | 以 PR 為單位：把範圍內所有非 merge 提交的宣告聯集起來。至少要有一個宣告；每一個宣告的裁決都要存在於 base |
| B | 以提交為單位：每一個改到 `program` 檔案的提交都要有自己的宣告 |

A 的理由：一個 PR 裡常有「主要的修改」加「解凍範例」「補測試」幾個提交，逐一要求宣告是形式。B 比較嚴，但對應的風險（同一個 PR 夾帶另一件沒有依據的修改）靠 PR 審查比較實際。

A 之下的細節：範圍內只要有一個提交宣告了 `Ruling: none`，報告就列出提醒，即使其他提交有裁決編號。

### B-6　「裁決存在」的定義

| 選項 | 定義 |
|---|---|
| A | base 的 `decision-log.md` 有 `## D-nnn` 的標題（與事實 6 相同的比對） |
| **B（建議）** | A，而且該裁決的狀態是 `accepted` |

B 的理由：依據一個已被取代（`superseded`）的裁決來建構，應該被看見。

B 的代價：要解析 `### Status` 之後的那一行。D-013～D-016 的寫法不同（事實 12），實作前要先看它們，必要時把狀態的寫法整理一致（那是修改 `decision-log.md`，要修法）。若整理的成本高，先做 A，B 另外排。

### B-7　怎麼啟用

判決程式（`harness-core/`）是不分專案的核心，規則要能由專案決定開不開。

- **A（建議）**：清冊加一個指示，例如 `@build-ruling required`，沒有這一行時行為與現在相同。作法與 `@coverage`（D-060）一致。
- B：直接寫死在判決程式。

啟用的時機：CI 的判決程式與清冊都取自 base，所以修法 PR 合併之後，**下一個 PR 起**生效。當時已經開著的建構 PR 會被要求宣告；它們的提交標題大多已經帶裁決編號（事實 9），預期不用改。

### B-8　分批

全部照建議時：

1. **修法 PR**（要簽章）：
   - 本裁決（`decision-log.md`）。
   - `harness-core/law_check.py`：讀提交訊息、比對宣告、報告與提醒；版本升為 0.9.0。
   - `harness-core/tests/`：測試。至少涵蓋：宣告的裁決在 base 上存在而通過；只在 head 上存在而未通過；沒有宣告而未通過；`Ruling: none` 通過並列出提醒；只改文件的 PR 不需要宣告；清冊沒有指示時行為不變；merge 提交不算。
   - `harness-core/README.md`、`law/README.md`：說明。
   - `law/manifest.txt`：加上指示（啟用）。
2. **修法 PR 二**（要簽章，可以併進第一個）：給 AI 的指示（`AGENTS.md`、`.ai/rules/`、各工具的指示檔）寫明宣告的寫法，以及「依據待簽的裁決先做建構時，分支疊在修法分支上」。這是 `03-harness-plan.md` 2-4 期的一部分。
3. **文件**（不用簽章）：`03-harness-plan.md` 第三節 P4 的現況、`12-escaped-defects.md` 要不要記一筆（這次沒有漏網，是在合併前發現的）。

沒有建構 PR：`harness-core/` 整個是律法（gate），程式的修改就在修法 PR 裡。

要先驗證再啟用：判決程式改好之後，先不加清冊的指示，對 `main` 上看得到的 25 個 `build` 提交各自所屬的 PR 回放一次，確認結果符合預期（24 個通過、1 個要求 `Ruling: none`），再啟用。

## 六、這個機制做完之後仍然擋不到的

寫在這裡，是因為之後訂定本專案 harness 的有界主張時要用。

1. 宣告了不相干但存在的裁決編號。
2. 把有依據的建構宣告成 `Ruling: none`。報告會列出提醒，要靠負責人看。
3. 改了行為、但沒有範例涵蓋那個行為的建構（第三節）。這要靠擴大範例的涵蓋，不是本題。
4. 直接推送到 `main`，或用管理員權限繞過保護規則（與修法機制相同）。
5. 裁決已經在 base，但建構做的事超出裁決的範圍。內容對不對，機制不判斷。

## 七、起草時沒有確認的

1. 「從 `main` 開分支的同樣修改不會被擋」是讀判決程式得到的，沒有開 PR 實測（事實 3）。
2. 回溯檢查只涵蓋本機看得到的 147 個提交，而且比對的是提交當下的檔案（事實 9～11）。
3. D-013～D-016 的狀態寫法沒有看（事實 12）。
4. 標題裡的 `D-nnn` 會不會出現「提到但不是依據」的用法（例如「不屬於 D-050」），沒有在歷史裡找到，但沒有窮舉。
5. GitLab 的接法（2-3 期）還沒做。提交訊息的作法不依賴平台，但沒有在 GitLab 上驗證。
6. 人直接在 GitHub 網頁上修改檔案產生的提交、`revert` 產生的提交，訊息格式是固定的，會不會被新規則擋下，沒有試。
