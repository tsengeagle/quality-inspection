## 1 問題與主張

- 生成的程式碼會削弱「看起來怪怪的」這種線索的證據價值。誤解需求的程式一樣能編譯、讀起來通順，同時悄悄漏掉一個欄位、把判斷條件寫反，或退回主流慣例。
- 所以把生成器視為永遠不可靠。這是信任政策，不是對模型能力的預測。
- 設計問題因此變成：驗證堆疊要包含什麼？什麼理論能告訴我們它對某個適配主張是否足夠？
- 答案取自 Alexander 1964 年的《形式綜合論》：適配只能從反面得知。只要相關的不適配能列舉並機械偵測，綜合就從設計問題變成技術問題。
- 列舉永遠不會完成，也不是每個被認出的不適配都做得出偵測器。所以列舉本身是受治理、持續成長的產物。

五項貢獻：設計理論本身；「非原生的在地建構者」模型；四形式模式語言；雙迴路與 S = P = T = W；對 Alexander 1996 年挑戰的分級回答。作者強調這五項是一條鏈，不是五個獨立主張。

## 2 理論背景

### 在地建築為什麼不需要建築師

在地建築文化沒有人掌握全局模型，卻能達成適配。建構者遵循傳統，傳統是已解決的不適配的記憶，也包含禁忌。傳統有黏滯性，會抗拒改變，所以每一代都從已知良好的形式出發。現實讓剩下的不適配顯現出來，例如屋頂漏水，然後就地修正。

這個過程成立有三個通常沒被說出來的條件：

1. 顯現是物理的：失敗會自己變成感官訊號。
2. 感知是同處的：承受、注意到、能修復的人都住在建築裡。
3. 詮釋是文化的：傳統預先決定了什麼算不適配。

這三個條件對 LLM 建構者都不成立，所以每一項都要用工程方式補回來。

Alexander 自己遇到條件不成立的場合（現代大學校園）時，設計了補救機制：《奧勒岡實驗》的定期診斷，依模式語言評分，結果連到修繕預算。這是「把感知制度化」的先例。

### 模式語言是鷹架

Alexander 後來的立場：隱性的共同語言已經瓦解，要用明確的模式語言重建傳統，最終目標是重新內化。大師級建構者終將「不再需要這套語言」。論文稱這個終點為 Alexander 的遺忘。P9 反轉的就是這一點。

### 問題框架

Michael Jackson 的問題框架用來陳述問題。問題在世界裡，機器是解法。把問題歸到一種框架類型，就繼承了該類型已知的關注點，等於一份預先列好、可重複使用的不適配清單。專案仍要在這之上列舉自己領域特有的不適配。

### 推導的性質（2.5）

- 表 1 的每一列：一個古典命題，加上「建構者是非原生的 LLM」這個前提，推出一項工程義務，再配一個履行它的機制。
- 推導固定的是義務。機制是工程選擇，不是唯一做法。
- 推導成不成立，看的是每項義務是否從命題和前提推得出來，不看歷史上先有哪個。
- 十列不宣稱完備，也不宣稱互相獨立。
- 宣稱的是統一性，不是排他性：有些義務用別的軟體工程理論也講得通。重點是十項都出自同一套對適配的說明。

十條義務的表見 `01-mgd-concepts.md`。

## 3 方法論

### 律法與 harness 的界線

用角色劃分，不用執行時間劃分。有規範的權威但不能做判決的，屬於律法。能做判決或停止進度的，屬於 harness。閘門刻意橫跨兩邊。

一個容易忽略的要求：**驗證不止於生成的程式碼。律法本身和執行它的機制也要被驗證**，檢查內部一致性和對來源的忠實度。這不會無限後退：鏈條終止於可以機械查詢的主要脈絡，或授權該代理的人類裁決。

### 3.1 雙迴路

- 人設計律法，LLM 把它非確定性地轉成候選程式，候選程式進入內迴路，反覆面對確定性的驗證。
- 內迴路裡人可以幫忙（批准一個操作、回答規格的問題），但不評判候選程式。
- 內迴路反覆失敗時，不再歸咎一個個候選，而是上報外迴路診斷。
- 漏網的缺陷觸發對治理鏈的診斷。律法已經寫了這項期望，就是偵測的問題：偵測器不存在、無效、掃不到，或讀到過時的代理。律法沒寫，就是律法的遺漏或世界的新要求。
- 修訂只發生在設計期，不在內迴路裡。

### 3.2 問題側的規格

- 每個使用案例歸到一種框架類型後，用五種產物描述：框架檔（類型、問題世界的事實、關注點）、需求檔、機器規格（職責、輸入輸出、對外端點）、領域規格、驗收檔（Given–When–Then，可追溯到需求）。
- 規格是一個使用案例一個使用案例寫的，不是事先全部寫完。隨系統一點一點長出來。
- 七種框架類型：五種來自 Jackson（受命行為、簡單工件、必要行為、資訊顯示、轉換），加上作者自訂的反應式調用和連接框架。
- 規格語言本身有機器檢查：JSON Schema 約束檔案格式；39 條規則的 linter 檢查格式、跨檔追溯、結構、跨框架一致性；一份受控的語意標籤詞彙，每個標籤對應必然的程式後果。
- 這些（框架目錄、schema、linter 規則、語意詞彙）也只能經由人類修訂。
- 規格樹用聚合和 bounded context 組織，所以問題側的分解單位和解法側的套件單位相同。
- **框架類型和架構無關，但規格的表徵依架構而定。**
- 寫規格之前先辦 Event Storming 工作坊，領域專家和開發者一起排出事件時間線。命令、讀取模型、政策再依作者自訂的規則對應到框架類型。

### 3.3 解法側的模式網路

- 模式網路在任何提示詞、閘門、工作流程存在之前就先畫好。
- 它是工程選擇，不是理論的一部分。作者的網路是他們團隊 2018 年以來累積的架構文化。
- 網路是選擇性的：只收團隊有約束用法的模式。
- 巨觀結構是三條具名規則：分層規則、依賴規則（只能向內）、跨界規則（層與層只在 port 相會，領域物件不跨界）。三條都由機器檢查。
- 每種框架類型有一份工作流程，是模式網路上一條有序的走訪路徑，決定生成順序。
- 局部性：聚合劃出修復應該停留的範圍，事件是聚合之間刻意保持的弱耦合。這些邊界限制修復能擴散多遠，但不能強迫建構者把修改留在邊界內，所以還需要回歸防護。
- 先畫語言、再用閘門強制，讓各個提示詞不必在生成時互相協調，因為相容性已在語言層級規定好。

### 3.4 四形式模式語言

四種形式見 `01`。補充幾點：

- 四種形式是分工，不是重複。準則解釋何時與為何；範本給正面形式；禁則記下和模型預設不同的在地做法，也是修復時的錨點；只有閘門做出權威判決。
- 「必須有某個構造」寫成「禁止它不存在」。
- 規則在多處被消費（準則、給建構者的指引、閘門的規則目錄），所以每條規則指定一份正本，登記在單一權威來源的登記表。其他地方是完整重述而不是指標，因為建構者生成時必須看得到規則。機器可讀的連結把重述綁回正本，副本走樣時一致性檢查會失敗。
- 每次工作階段開始、建構者生成任何東西之前，自我一致性檢查會重算在多處被宣稱的事實。
- 退役的準則也要管：舊措辭可能以指引的形式重新出現，所以有一份反模式登記表和掃描器。刪除只發生一次，遺忘卻要持續強制。

### 3.5 閘門堆疊

撰寫當時有 28 道阻擋性閘門，分五類：

| 類別 | 數量 | 檢查什麼 |
|---|---|---|
| 規格品質 | 1 | 規格的 linter |
| 雙 profile 測試 | 1 | 每個生成的測試加上常駐的架構測試，在記憶體和完整資料庫兩種設定下都要過 |
| 逐使用案例的結構閘門 | 18 | 生成的程式和測試是否在結構上忠於規格 |
| 聚合層級的收官閘門 | 7 | 規格邊界、交付物清單、封裝、跨框架一致性 |
| 確定性審查 | 1 | 188 條機器可檢查的規則 |

另外有不阻擋的建議性閘門，以及一個選用的多模型語意審查。後者刻意放在機械化清單之外，因為它不是確定性的；它的發現交給人裁決。

18 道結構閘門分三族：

- **涵蓋閘門**：每個情境和每條契約條款都有對應的測試；沒有測試引用規格未宣告的情境；測試斷言的結果類型和情境宣告的相符，並提到情境點名的狀態和引號內的值。
- **欄位閘門**：規格宣告的欄位必須在它經過的每一站重新出現，名稱、型別正確，而且真的被帶著走。反向檢查（沒有未宣告的欄位）只對事件紀錄是阻擋性的，因為事件欄位會進入永久紀錄。
- **控制器閘門**：請求物件、端點語意、錯誤處理、控制器測試的完整性。

一個重要的觀察：**欄位在鏈條中途消失時，每一層單獨看都是正常的**。只有逐站、逐欄位檢查整條鏈才看得出來。

閘門密度跟著「強制的物理」走：編譯器自動拒絕的不用再擋，平台既不預防也不暴露的違規（例如封裝和分層）才需要明確的偵測器。

確定性是必要條件：內迴路裡沒有人能仲裁，所以同一個產物每次都要得到同一個判決。否則違規數量無法顯示修復有沒有進展。

### 3.6 修復迴路

三層：測試失敗、結構違規、模式違規。每一輪只處理一層的違規。五個性質：

1. **批次處理**：重新驗證便宜，修復昂貴，所以每輪收集該層回報的所有違規一起修。
2. **以傳統為錨的修復**：違規送到建構者手上時，附上違規的程式、違反的規則、指向傳統文件的指標。修復時最容易漂回主流寫法，因為生成時讀過的模式可能已經不在上下文裡。
3. **回歸防護**：每輪修復都重跑先前的閘門。
4. **停滯偵測**：違規數連續三輪沒有減少，迴路停止並上報給人。生成前也一樣：建構者看不懂規格時，停下來問人，不靠猜。
5. **脈絡凍結**：整個修復期間，評判的依據固定不變。穩定讓收斂成為可能，但不保證收斂，所以才有停滯閥。

合起來的意思：沒有哪一輪需要一次修對所有東西，只要違規數下降、不弄壞已通過的即可。

### 3.7 建構者不能碰什麼

- 在地文化裡，修復的經驗會回流到傳統。這條通道被刻意切斷。
- 建構者不能寫入閘門判決和工作流程狀態，有防護機制拒絕。否則它可以直接改寫「自己有沒有通過」的證據。
- 傳統檔案的保護方式不同：建構者實際上改得動，但這種修改沒有立法效力。一致性檢查會偵測到變更，並標出不再一致的相依文件。
- 傳統的修訂有三個來源：缺陷的事後檢討、生成過程中注意到並留待批次審查的改進、對驗證產物本身的稽核。模型可以動手改，人決定是否接受。

## 4 理論分析

### 4.1 非原生的在地建構者

- 偏離不是隨機雜訊，而是持續拉向訓練時學到的主流模式。
- 上下文可以改變行為，但不能證明學到的預設已被取代，所以方法論當作那股拉力仍然存在。
- 禁則目錄記錄的就是主流慣例和在地準則衝突的地方。

三個後果：強制必須壓過指引；守護反主流準則的規則不因統計上的安靜而退役；偏向和能力來自同一個來源，所以傳統不必重述共通知識，規模才可能控制得住。

### 4.2 主要脈絡與代理脈絡

見 `01`。補充三個實務後果：

1. **假綠燈**：產物適配代理卻不適配主要脈絡時，所有對代理的檢查都是綠的。
2. **閘門密度**：集中在不適配不會自己顯現的地方。
3. **指定正本**：主要脈絡無法直接查詢時，要有一份代理當作機械核對的正本。

### 4.3 偵測成本

每多做一次檢查的成本，決定回饋能有多頻繁。機器在外迴路仍然幫得上忙：提醒太久沒審查、蒐集證據、保留紀錄。但機器的判斷不能取代人對「規格是否仍適配世界」的判斷。機器能檢查的是這個判斷有沒有被做出來。

### 4.4 切斷的回流

讓生成器修訂傳統，等於把律法暴露在它本來要約束的那些預設之下。

結果是一種混合體：把無意識過程的修復動態機械化，嵌在有意識的立法機構裡。會壓垮設計者的修復工作交給內迴路；傳統可以慢慢變，因為例行修復不再等它。

### 4.5 永遠的新手

- 問題不是建構者能不能學會在地傳統，而是能不能證明它已經內化到可以撤掉鷹架。
- 觀察產出能提高信心，但提供不了撤除所需的保證。衡量到的可靠度是關於建構者的證據，不是關於某個特定產物的判決。
- 傳統本身一直在變，所以任何內化都只是某一刻的快照。
- 反駁「harness 是外部記憶，建構者不就記得了嗎」：記憶是真的，但它在建構者之外，是被強制的，不是被擁有的。
- 反駁「微調呢」：可以減少需要提供的指引，但不構成撤除驗證的理由。
- 人類則可以走 Alexander 原本的路。但內化能撤掉的是指引，不是驗證。

## 5 實證（Java 參考實作）

### 規模

| 項目 | 數字 |
|---|---|
| 問題框架規格 | 64 份，約 500 個 YAML 檔、約 40,000 行 |
| 驗收情境 | 310 個 |
| 契約條款 | 547 條 |
| 阻擋性閘門 | 28 |
| 確定性審查規則 | 188（其中 95 條永遠啟用） |
| 規格 linter 規則 | 39 |
| 自我一致性檢查 | 21 |
| 架構決策紀錄 | 53 |
| 模式與準則文件 | 約 145 份、約 57,000 行 |
| 腳本及其回歸測試 | 約 130,000 行；閘門模組的測試超過 3,500 個 |
| 生成的後端 | 336 個正式檔案（約 24,000 行）、201 個測試檔（約 40,000 行） |

值得注意的比例：

- **規格比它生成的正式程式碼還長**（40,000 行對 24,000 行）。約一半是格式和重複結構。
- **最需要人判斷的內容約佔規格的 27%**：驗收情境、契約、行為規則、需求。
- **harness 遠比被治理的程式大**：腳本和測試約 130,000 行。

### 做法

- 2025 年 7 月開始，持續進行。每次換模型就從空目錄重建後端。閘門或模式改了，也刪掉所有生成的程式重來。
- 每次重建都要通過一套端對端測試。這套測試由人維護，從不隨後端重新生成，透過不變的前端執行。它是跨重建固定不變的回歸基準。
- 綠燈的重建不只要求零違規，還要有證據顯示每道阻擋性閘門都真的跑了。跑不了的閘門算跳過，不算通過。
- 前端只生成一次，經人直接驗收，之後不再重新生成。理由是成本：只生成一次的東西負擔得起人工驗證，不斷重新生成的後端負擔不起。
- 每種框架類型的第一份規格由作者手寫，之後由模型依範例生成、作者審閱修訂。
- 閘門由模型撰寫，但檢查什麼由作者決定。

### 遙測

2026-03-01 至 2026-08-16，5,807 次確定性審查，回報 216,148 筆違規。去除重複後是 1,748 個不同的「規則加檔案」位置，分布在 235 條規則（歷史聯集）。違規位置最多的八條規則裡，六條守的是在地的測試寫法。這些數字顯示違規集中在哪裡，不說明原因。

測試強度（PIT 的 mutation 分數）是 95% 到 100%。作者特別提醒：這個分數完全不說明測試是否忠於驗收情境。

### 三項觀察

1. **局部正常的產物，在交界處仍可能不適配。** 聚合收官時反覆找到逐檔檢查抓不到的缺陷：服務從未讀取的輸入欄位、永遠不會執行的錯誤分支（導致規格定義的錯誤全變成 500）、從儲存重建時丟失衍生狀態的轉換程式、規格定義卻沒接線的跨聚合反應。每個都催生了新閘門。悄悄修掉單一缺陷就繼續往下走，是不被允許的。
2. **代理會漂移，偵測器自己也會。** 稽核驗證產物時在多個層次找到同一類失效：文件裡的數字和規則對不上、hook 還在檢查已退役的準則、閘門因為掃描範圍悄悄縮小而通過、驗證器自己的註解還把一支已停用的腳本算作有接線。
3. **寫在提示詞裡的指引一再被違反，對應的閘門抓到了。** 專案最初只有文字和範例程式，沒有可執行的檢查，同類違規持續出現。之後才一道一道加上確定性閘門。

### 證據的限制

一個專案、一種架構、一種技術棧、一位主要立法者，而且這位立法者同時是領域專家。所以需求發掘、規格撰寫、領域知識分散在不同人身上的情況，這個案例沒有評估。它展示的是可行性，不是可移植性。P4、P5、P7、P9 有機制，但沒有個別量測。

## 6 回應 Alexander 的挑戰

| 挑戰 | 回答 |
|---|---|
| 生成性：語言能不能生成整體，而不只是零件目錄 | 操作上回答了。LLM 能照字面解讀模式語言，harness 確定性地治理它的產出 |
| 整體性 | 形式上回答了（各部分可驗證地組合起來）。Alexander 說的「感受到的整體性」沒有機械化，也不宣稱 |
| 道德面：它讓生活更好嗎 | 找到位置，沒有機械化。它是 S–W 關係，沒有閘門到得了 |

延伸的論點：

- 例行的建構和修復交給機器後，程式碼不再是人日常閱讀和修改的東西。人的工作層次上移到發掘問題、寫成規格、維護傳統。
- 但程式碼不因此變得陌生。四種形式把建構者限制在團隊自己的傳統裡，所以有人需要下去讀程式時，讀到的是符合自己傳統的程式。作者沒有宣稱生成的程式更好懂。
- 一個位置還不是一個制度。作者提議「定期的居住審查」：人定期判斷系統是否仍服務使用它的人，結果留下紀錄、追溯到相關的框架、回饋到律法的修訂。這還沒有建立。
- 內迴路是為外迴路服務的。把機器可判定的三項關係變成例行公事不是目的，目的是把人的注意力釋放給第四項。

## 7 與既有做法的關係

- **軟體模式運動**：缺的不是洞見，而是可治理的執行者。模式的應用一直依賴人的詮釋。
- **規格驅動開發**（例如 Spec Kit）：把意圖外化成持久的結構化產物。MGD 問的是邏輯上更早的問題：這條路徑外面的驗證邊界要確立什麼，「沒偵測到不適配」才足以支持適配主張？因為規格和執行它的偵測器自己也會走樣。
- **安全關鍵系統的保證論證**：靠排除已辨識的反駁來建立信心，和不適配列舉的負向邏輯很接近。差別是 MGD 要求清單上每一項都落實成確定性的偵測器，而且偵測器的活性也要被驗證。
- **自我修復、自我除錯的研究**：可以放在修復迴路裡當修復策略，但不能取代決定「哪些不適配會被顯現」的閘門堆疊。
- **護欄與可執行約束的研究**：都印證了「自然語言指示不足以確保遵循」。MGD 多問的是充分性、代理與偵測器如何保持有效、誰能修訂。
- **harness 自動演化的研究**：帶出一個治理問題。harness 改寫自己時，是在改進機制，還是在修訂定義正確性的規範？後者必須經過人類。

所有這些做法都有同一個殘餘風險：產物可以通過每一項既有的檢查，同時違反沒有檢查涵蓋的需求。MGD 不消除這個風險，只是從不宣稱絕對的適配。

## 8 限制與未來工作

1. **外部效度。** 可移植性的主張是可否證的，檢驗方式是第二個繫結。若某項義務在符合前提的繫結裡無法履行，或者前提成立時拿掉義務卻不損失它要保護的性質，理論就被否證。單一實作失敗不算反證。
2. **問題與解法只分開了一部分。** 驗收情境和框架裡的論證仍引用解法側的產物、使用解法家族的詞彙。完成分離會讓「問題保持固定」變成 harness 能檢查的性質。
3. **換架構家族**（例如 CRUD 三層式）：框架類型可以保留，但需要自己的規格 schema、分解單位、模式網路、閘門集合。義務不變。這是尚未測試的預測。
4. **理論規定的是如何驗證對所選脈絡的適配，不規定脈絡要包含什麼。** 專案把架構結構排除在脈絡之外，拿掉的是律法裡的規則，不是理論裡的義務。
5. **S–T 是最弱的一環。** 測試是 LLM 從驗收情境翻譯來的，機器只檢查結構。程式被檢查兩次（結構閘門、跑測試），測試只被結構檢查一次，卻是評判程式行為的基準。三個補救方向，由便宜到結構性：
   - 把規格裡每個預期值追到測試的一個斷言。
   - 變異規格：改掉一個預期值、只重新生成測試、對不變的程式執行，測試應該失敗。在測試仍由 LLM 生成時，這只能當建議。
   - 讓翻譯確定化：由驗收規格直接推導出測試和斷言。信任於是集中到翻譯器，翻譯器要像 harness 其他部分一樣被驗證。
6. **閘門內部的漏評。** 閘門跑不了會算跳過；但閘門內部某個偵測器的掃描範圍悄悄變窄，仍可能通過。逐項回報「有幾項沒評估到」還是未完成的工程。
7. **阻擋性閘門只圍住後端。** 前端和後端各持有一份 API 契約的圖像，欄位名稱、日期格式、列舉值互相漂移，兩邊的測試和型別檢查都是綠的。只有端對端執行才看得出來。
8. **成本沒有量測。** 建 harness 和寫規格的工作量都沒有量。理論預期 harness 的成本很可觀。兩個因素限制成本：傳統主要只需寫下模型預設無法可靠提供的東西；框架關注點可以跨同類問題攤提。是否回本，沒有量測。
9. **不划算的場合。** 成本要靠反覆重新生成來攤提，所以在探索性原型、一次性工具、架構還在摸索時，買到的很少。
10. **上下文視窗也是成本。** 指引寫得超過正確性所需，就會和生成本身搶上下文。一組學生手寫的指引長度約是模型起草版的一半，生成一樣可行，但寫得慢很多。作者的解釋是人比較看得出哪些在地選擇是模型預設不會提供的。閘門沒有這個限制，因為它們在生成的上下文之外執行。
11. **外迴路還不是制度。** 定期的居住審查、每個框架記錄「要改善誰的工作」的欄位、非工程人員參與撰寫框架，都還沒有完成。

## 附錄 A 形式化

- **不適配謂詞**：對固定的治理表徵，每個機械化的不適配是一個可判定的謂詞，輸入是一個候選產物（程式加測試），輸出是有或沒有。
- **適配**：清單上每個謂詞都回報沒有。
- 三個性質：
  1. 適配相對於清單。對清單以外的事什麼都沒說。
  2. 適配是可判定的，因為每個謂詞都被設計成可判定。
  3. 適配相對於實際被評估的子集。偵測器找不到它要檢查的對象時，謂詞是沒被評估，不是評估為通過。只有被評估的子集等於整份清單時，才能主張對整份清單的適配。
- 「認得出」和「機械化」是兩回事。人可以認出一類不適配並做出裁決，而它仍然做不成可判定的謂詞。清單只包含機械化的那些。
- 對表徵的檢查、偵測器的確定性、夾具和可達性檢查，是信任判決的前提條件，不是適配定義裡的額外條件。
- **充分性相對於主張**：harness 足夠的條件，是它履行了支持那個有界主張所需的每一項義務，包括「被評估的等於整份清單」的證據。
- **S = P = T 的語意**：
  - 結構符合（S–P）：規格宣告的每個元素在程式裡有實現，而且一路上保持一致。反向只對事件紀錄和聚合根的公開行為是阻擋性的。
  - 情境涵蓋（S–T）：每個未被延後的驗收情境都有測試，斷言對照情境的結果分類做結構檢查。測試引用未宣告的情境是阻擋性的；正確引用的測試額外斷言了什麼，不檢查。
  - 執行：程式在每一種基礎設施設定下通過所有測試。
- 不得把規格未宣告的東西當成需求來實作或測試，因為那等於加了一條沒有人裁決過的需求，也就是修訂了律法。
- **偵測成本的界限**：可持續的回饋頻率，不超過該類資源的預算除以每次偵測的成本。

## 綜述篇多出來的內容

### 兩個版本在義務上的措辭差異

- **P4**：綜述篇凍結的範圍更明確：規格、傳統、閘門、框架版本。
- **P8**：綜述篇把重點放在權限而不是「無法形式化」：挑選不適配的準則可以被形式化，但準則本身必須由誰來選定，這個權力留在人類手上。
- **P9**：條件是知識論上的，不是對能力的主張。閘門只能由人類裁決撤除。
- 綜述篇明說這些命題是作者的綜合整理，不是 Alexander 本人列出的清單。
- 義務約束的是「接受這些條件、並以支持適配主張為目標」的流程，不是所有 AI 編碼工作流程。

### 繫結與檢驗工具

- 繫結：某種架構為共用規格所寫的四形式模式語言與 harness，包裝成一個 Claude Code plugin。
- 系統是 Scrum 管理後端，四個聚合，70 個使用案例。
- 兩種檢驗工具**從不交給建構者**，但沒有對 harness 的開發保密：
  - 185 個端對端測試，透過固定的前端執行。
  - 1,323 筆 HTTP 請求的語料，由端點規格推導，獨立於任何生成的程式碼，用來比對 Java 和 Go 的回應。
- Java 系統是行為的參照，不是標準答案：兩邊共有的錯誤不會顯現。
- 黑箱比對是報表，不是閘門。一筆分歧提出一個問題，而不是解決它。

### Go 繫結的做法

- 從模式語言開始建（P3）。讀同一份規格，經由一個確定性的投影翻譯或去掉 Java 專屬的鍵。
- 架構是三層式、每個使用案例一個程序、每張資料表一個 SQL 包裝。
- P5 的機制不同：把每個使用案例的修改限制在所屬聚合的目錄內，限制使用案例之間的匯入，每輪修復後重跑先前使用案例的測試。
- 修復迴路是一支獨立的程式，每一輪開啟一個新的建構者工作階段。
- 防護機制還原所有超出修補範圍的修改。
- 無人值守的執行期間，防護也阻擋對規格和傳統檔案的寫入。

### 凍結協定下的結果

律法和 harness 凍結在同一個 commit，三家廠商的八個建構者各自從空目錄嘗試全部 70 個使用案例。共 18 次執行。

- 14 次完成，每個聚合都通過收官。
- 其中 13 次（來自五個建構者）在 1,323 筆請求上與 Java 完全一致，並通過全部 185 個端對端測試。
- 第 14 次（較弱的模型）通過每一道閘門，卻有 15 筆分歧。
- 4 次停在同一個使用案例（一張燃盡圖），原因是修補次數上限或時間預算。
- 只給規格、沒有 harness 的探索性執行，分歧在 101 到 808 筆之間。
- 任兩個完成的建置，沒有任何一個使用案例檔案完全相同：架構相同，程式不同。

作者的保留：沒有凍結的對照組，不主張是 harness 造成了一致。這些執行回答的是不同建構者能否執行同一份協定，不是比較它們的能力。

### 兩個失敗分析

**見證比規則窄。** 規格規定只有空白字元的會議時長視同省略。驗收情境的例子用的是空字串。較弱的模型只把空字串當成省略，照情境寫的測試通過，每道閘門都過。那 13 次一致的建置都正確處理了空白字元。這帶出一個觀察：能力強的建構者可能只因為沒犯下 harness 偵測不到的錯，就讓 harness 的弱點沒有顯露。

**律法自己不一致。** 一條規則讓衝刺到期時自動開始，以可設定的週期檢查。寫入防護不讓使用案例的修改碰共用設定，律法又允許用固定值當退路，而需求排除固定值。模型兩者都遵守。每道閘門都過，185 個端對端測試只過 79 個。另外兩個模型用防護沒檢查的 shell 指令改了設定，通過全部 185 個。

處理方式：人類裁決允許修改共用設定並移除退路；harness 放寬防護，並加一道依規格檢查設定變數的新閘門；shell 寫入的缺口另外補上。之後重新生成受影響的使用案例，通過 185 項中的 184 項，剩下一項不穩定的測試重試後通過。

兩句結論：

- 系統可以滿足每一條被強制執行的規則，卻違反這些規則要保護的需求。
- 系統也可以通過行為測試，卻違反規則。

### 誰來驗證驗證者

- 治理機制本身也是軟體，大部分由 LLM 撰寫。
- 每當 harness 改變都要問：這是改進機制，還是修改定義正確性的規範？前者是工程，後者是立法。
- 目前的答案是四樣東西：夾具顯示每道閘門仍會觸發；可達性檢查顯示它掃描到它宣稱的範圍；代理脈絡的核對；一本記錄每個漏網缺陷與裁決的帳本。
- 通用的答案仍是開放問題。
- 人類權威建立的是問責，不是無誤。

### 對規格的看法

- 規格成為核心的工程責任。
- 權威不等於充分：重建時必須保住的東西，也存在於模式語言、harness 和驗收測試之中。
- 共用規格裡和繫結相關的條目，刻意以主版繫結的詞彙撰寫。許多專案只需要一個繫結，中立的定義語言會讓規格寫起來比較不自然。轉接成本由第二個繫結承擔。中立的定義語言與 MGD 相容，但尚未測試。
- 閘門和律法是依框架類型和模式語言寫的，不是依 Scrum 領域寫的。所以對同一繫結下、相同框架類型的其他領域，大多應該仍然適用。這個移轉尚未測試。
- 教育應該著重問題分析、契約、驗收情境，以及撰寫傳統的能力：知道哪些在地選擇是模型的預設無法可靠提供的。

### 其他限制

- 兩個繫結共用同一個問題領域、同一位主要立法者、同一個代理程式 CLI。
- 維護律法和 harness 的成本沒有量測。
- 只由人類核准規則，可能形成瓶頸。
- 檢視一直是由不適配觸發、即時進行的，還沒有以排程方式檢視使用中的系統。
