## 一、問題

後端的回應形狀已經是律法：`specs/*/http.yaml` 是封閉的形狀，由觀察式的比對閘門對照後端實際的回應（D-061、D-088）。

## 三、有哪些作法

| 代號 | 作法 | 擋得到（事實 1 的 a～f） | 成本 |
|---|---|---|---|
| T | **前端的回應型別由契約產生**。一支產生器讀 `http.yaml`、`http-common.yaml`、`model.yaml` 的列舉，產生 TypeScript 的型別；service 與假回應都用這些型別 | a、b、c；d（列舉變成型別） | 產生器；把手寫的 dto 換掉；假回應要掛上型別；E2E 要加型別檢查 |
| V | **假回應在執行時由契約驗證**。E2E 與單元測試的假回應經過一個輔助函式，用契約的形狀比對，不符合就讓測試失敗 | a、c；b 只有在有人寫了那種形狀的假回應時 | 要用 TypeScript 再寫一次形狀的比對（後端的 `JsonShape` 是 Java）。同一份律法有兩個比對器 |
| R | **假回應改用後端實際的回應**。後端的測試已經在記錄每一筆回應（`HttpObservationRecorder`），把它們存成檔案給前端當假回應 | a、b、c | 檔案要提交或跨工作傳遞；前端要的情境（特定的資料）後端的測試不一定有 |
| L | **E2E 打真實的後端**。把事實 7 的流程放進 CI，並擴充情境 | a～e 都擋得到，只要有那個情境 | 最高：CI 要起後端與資料、要有各角色的登入、情境要一個一個寫 |
| C | **涵蓋要求**：前端呼叫的端點，契約裡的每一種形狀都至少要有一個假回應 | b | 搭配 T 或 V 才有意義 |

沒有一種作法擋得到全部。f 與契約無關，只有真的點那個按鈕的測試擋得到。

## 四、待裁決

### G-1　做哪幾種

| 選項 | 內容 |
|---|---|
| **A（建議）** | 先做 T（型別由契約產生）加上 C 的最小版本；L 另立一題；V、R 不做 |
| B | 只做 V |
| C | 直接做 L |

A 的理由：

- T 把檢查放在編譯期，不用另一個執行期的比對器。這個專案的原則是不建立第 N 套 binding（`docs/harness/README.md`）；V 等於用 TypeScript 再實作一次 `JsonShape`，兩邊的語意會漂移。
- T 對「裁決改了後端的形狀，前端沒有跟著改」（E-05）最直接：型別一重新產生，用到舊欄位的前端程式就編譯不過。
- L 擋得到最多，但它是另一個量級的工作，而且它擋的是「有寫情境的部分」。建議在 T 之後做，先把固定的三頁流程放進 CI。
- R 的假回應來自後端的測試情境，前端要測的畫面狀態常常需要特定的資料，兩邊對不上。

### G-2　產生器放在哪裡、用什麼寫

| 選項 | 作法 |
|---|---|
| **A（建議）** | 放在前端（例如 `frontends/quality-inspection-frontend/tools/`），用 Node 寫，讀 repo 根目錄的 `specs/` |
| B | 放在 `harness-core/`，用 Python 寫，與 `spec_lint.py` 並列 |

A 的理由：產生的是 TypeScript，前端的工具鏈本來就有 Node。`harness-core/` 是不分專案的核心而且是律法，第二個專案也是 TypeScript 前端時再搬。

A 之下，產生器本身要不要列為律法，見 G-9。

產生器要有自己的測試，至少涵蓋：封閉的物件、可為 null 的欄位（`型別?` 與鍵結尾的 `?`）、字面值 `'null'`、陣列、列舉、`variants`、`$data` 與共用的外殼、`transition`。

### G-3　產生的型別長什麼樣子

- **A（建議）**：每個端點一個型別；有 `variants` 的端點是各形狀的聯集，每一種形狀另外有名字。可為 null 的欄位是 `T | null`（不是選填）；字面值 `'null'` 是 `null`；列舉是字串字面值的聯集，取自 `model.yaml`。
- B：只產生列舉與欄位名稱的常數，dto 仍然手寫。

A 之下，前端要處理聯集（例如案件詳情的 `full` 與 `metadata`）。#208 已經用「看回應的形狀」分辨了一次，型別產生之後這種分辨會由編譯器要求。

### G-4　契約改了之後，前端什麼時候要跟上（最需要想清楚的一題）

修法與建構分開（P4）：修法 PR 改 `http.yaml`，不能帶程式；建構 PR 之後才改程式。若產生的型別一律跟著 `specs/` 的現況，修法 PR 一改契約，前端就編譯不過，而修法 PR 又不能改前端：**卡死**。

後端有同樣的問題，解法是兩個：範例先凍結在 `known-test-failures.txt`（D-066 第 5 點），契約用 `transition` 過渡（D-094 第 10 點）。前端需要對應的機制。

| 選項 | 作法 |
|---|---|
| **A（建議）** | 產生的型別檔**提交進 repo**，當成前端目前「跟上的契約版本」。另有一份落後清單（例如 `frontend-contract-lag.txt`），列出型別檔與現行契約不同的端點。閘門的規則：實際落後的端點必須與清單完全相同。清單列為 `baseline` 類的律法：新增行要簽章（放在修法 PR 裡），刪除行免修法（建構 PR 重新產生型別、修好前端、把那一行刪掉） |
| B | 型別每次建置時產生，不提交；契約的破壞性修改一律靠 `transition`，產生器在過渡期間讓舊的前端仍然編譯得過 |
| C | 型別檔提交，過期時只提醒、不擋 |

A 的理由：它與已知失敗清單是同一個機制，核准者在修法 PR 上看得到「這次修法讓前端落後了哪幾個端點」，這正是 E-05 缺的那個訊號。B 要產生器理解 `transition` 並決定哪些欄位暫時放寬，規則複雜而且容易放寬過頭。C 的提醒在這個專案的經驗裡不會被處理（`05-current-state.md` 過期八天）。

A 的代價：多一份基線檔與一段比對的程式。落後清單長期不清空時，前端就一直編譯在舊的契約上；清單的長度要當成指標看。

### G-5　假回應怎麼接上型別

- **A（建議）**：提供一個有型別的輔助函式，假回應都經過它。例如 `contractResponse('GetReviewCaseDetail', 'metadata', { … })`，第三個參數的型別由前兩個決定。物件字面值多一個欄位（`isOwner`）或少一個必填的欄位，編譯就失敗。
- B：只把 service 的 dto 換成產生的型別，假回應不管。

A 的前提是 **E2E 的檔案要先有型別檢查**（事實 4）：加一個 `e2e/tsconfig.json` 與一個檢查的步驟。這一步不論其他題怎麼選都建議做，它很小。

TypeScript 4.7 沒有 `satisfies`，所以用函式的參數型別來檢查。物件字面值直接當參數時會做多餘欄位的檢查；先存成變數再傳就不會，這一點要在輔助函式的說明與測試裡講清楚。

既有的 58 處假回應（E2E 21、單元測試 37）要逐一改寫。改寫的過程本身就是一次全面的核對，預期會再找到幾個不符的地方。

### G-6　涵蓋：每一種形狀都要有假回應

- **A（建議）**：做最小的版本。前端呼叫的端點，契約的每一種形狀至少要被 `contractResponse` 用到一次；沒有用到的列出來，先只列出、不擋。清單清空之後再改成擋下。
- B：不做。

A 的理由：E-05 的原因是「根本沒有人寫過七欄的假回應」。T 讓寫錯的假回應編譯不過，但不會要求有人去寫。

## 六、做完之後仍然擋不到的

1. 前端自己的行為錯誤（事實 1 的 f、e）：要靠執行得到的測試。
2. 假回應的型別對、但值不合理（例如狀態是合法的值，但那個情境後端不會回這個狀態）。
3. 契約本身是錯的（E-10：契約照著有缺陷的程式立法）。前端會忠實地跟著錯的契約。
4. 落後清單裡的端點：在清掉之前，前端編譯在舊的契約上。
5. 請求的參數與本文（G-7 選 A 時）。

## 七、起草時沒有確認的

1. 產生器沒有試寫。`http.yaml` 的每一種寫法（特別是 YAML 的錨點、`$data`、`transition`）能不能都對應成 TypeScript 的型別，沒有驗證。
2. E2E 加上型別檢查之後會冒出多少既有的型別錯誤，沒有試。
3. 58 處假回應是用 `page.route(` 與 `.flush(` 數的，沒有逐一看；元件的測試直接給 view model 的不算在內。
