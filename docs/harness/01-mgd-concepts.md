## 一句話

把生成器視為永遠不可信任，把信任放在環繞它的、由人類治理的驗證機制上。

這是一項信任政策，不是預測模型會一直很弱。更好的模型提高的是機率，機率不能證明某個特定產物適配需求。

## 適配只能從反面得知

Alexander 的觀察：設計者很難正面描述「適配」，卻能指出一個個具體的「不適配」（misfit）。所以適配的定義是：**已列舉的不適配全部不存在**。

兩個直接的後果：

- 適配主張的強度只及於背後那份不適配清單，而清單永遠不會完成。
- 功能錯誤只是不適配的一種。程式功能正確，仍可能違反架構、契約或在地慣例。

## 律法、harness、建構者

| 名詞 | 定義 | 判別方式 |
|---|---|---|
| 律法（law） | 三樣由人類掌管的產物：說明要建什麼的規格、說明如何依在地傳統建構的模式語言、說明機器要檢查什麼的不適配清單 | 有規範的權威，但不做判決 |
| harness | 閘門、防護機制、修復迴路、表徵檢查，以及對它們自身的驗證 | 能做出判決或停止進度 |
| 建構者（builder） | 以 LLM 為核心的生成者，包含模型和它藉以行動的代理機制 | 產生和修復程式 |

每一道閘門都橫跨律法和 harness 的界線：規則屬於律法，執行規則的檢查程式屬於 harness。

寫進提示詞的律法只是指引（guidance）。指引能影響建構者，但不能做判決。

### 建構者前提

LLM 受過許多程式碼庫的訓練，卻不原生於任何一個。它偏離在地傳統時，會偏向主流慣用法，文章稱為偏向（bias current）。在地傳統只是以上下文的方式提供給它，沒有被內化。

十條義務裡有幾條的力道就來自這個前提。人類開發者不是理論裡的建構者，雖然同一批閘門放在 CI 裡也會檢查到人寫的程式。

## 兩個迴路與 S = P = T = W

- **內迴路**：機器節奏。閘門失敗就把候選程式送回修復，期間律法和閘門保持凍結。失敗先歸咎候選程式，不歸咎規格。
- **外迴路**：人類節奏。人類觀察系統的行為，修訂規格、傳統和閘門。主要產出是更好的治理規則，不是審查過的程式碼。

S、P、T、W 分別是規格、程式、測試、世界。等號只是助記，代表四項對齊關係，機械化程度不同：

| 關係 | 問的是 | 機械化程度 |
|---|---|---|
| S–P | 程式是否實作了規格宣告的每一項，而且沒有多做 | 閘門檢查選定的結構性質，例如每個宣告的欄位是否貫穿每一層 |
| S–T | 測試是否驗證了規格規定的每一項行為 | 只檢查結構上的對應。**這是機器檢查中最弱的一環** |
| P–T | 測試是否通過，並約束了程式的行為 | 是否通過完全自動；約束了多少則用 mutation testing 探測，未強制 |
| S–W | 規格是否適配世界 | 保留給人類 |

綜述篇另外區分三個層次：閘門合規（通過每一項列舉的檢查）、行為符合（行為符合獨立的外部測試預期）、確實服務了需要它的人。MGD 把第一項機械化，為第二項蒐集證據，把第三項保留給人類。

## 核心主張

**推導固定的是義務，不是機制。** 每個機制都只是履行義務的眾多選擇之一。

文章自己提出的檢驗方式是「第二個繫結」：問題固定，把解法側換成另一種架構或技術，看同樣的義務能否用不同機制再履行一次。

繫結（binding）的定義：某種架構為規格所寫的模式語言與 harness。依這個定義，本專案要建的 harness 本身就是一個繫結。

理論篇也說明，參考實作的閘門腳本、規則目錄、模式文件沒有公開；獨立重現需要依義務重新實作，而不是重用它們的產物。

## 十條義務

依理論篇表 1 與綜述篇表 1 整理。

| 義務 | 出發命題 | 工程義務 |
|---|---|---|
| P1 | 適配只能透過不適配得知 | 適配的主張以偵測器的判決為依據，絕不依生成器的信心 |
| P2 | 在地建築的不適配會以物理方式顯現 | 軟體的不適配不會自己顯現，必須人為製造顯現。每個偵測器要證明仍會觸發，也仍掃得到它宣稱掃描的範圍 |
| P3 | 傳統讓建構者從已知良好的形式出發 | 把傳統外部化並強制執行 |
| P4 | 逐一修正需要穩定的脈絡 | 每次修復期間，凍結評判修復的依據（規格、傳統、閘門、框架版本） |
| P5 | 修正要收斂，影響必須夠局部 | 在結構上限制修復的擴散範圍，並偵測漏出的部分 |
| P6 | 在地建構者同時承載傳統 | 把生成和制定規則的權限分開；建構者不得自行修訂律法 |
| P7 | 偵測成本決定負擔得起的回饋頻率 | 機器計價的檢查連續執行，人力計價的檢查按預算安排 |
| P8 | 選擇哪些不適配重要，本身需要判斷 | 定義和修訂不適配清單的權限留在人類手上；人類也判斷規格是否適配世界 |
| P9 | 明確的模式語言是鷹架，大師終將不再需要 | 不因建構者屢次遵循就撤除強制執行。遵循看得到，內化無法驗證 |
| P10 | 設計者依據脈絡的圖像工作，不是脈絡本身 | 建構者只能透過表徵看到脈絡，表徵會無聲漂移，所以表徵本身也要被驗證 |

補充：

- P1、P2、P4、P5、P7 不依賴建構者是 LLM，本來就是審慎的工程實務。P3、P6、P9、P10 的力道來自建構者前提。P8 介於兩者之間。
- 這十列不宣稱完備。漏網的缺陷先在既有的列裡回應；只有暴露出推導不出的新義務時，才加新的一列。

## 七條治理原則

理論篇第 3 節從表 1 提煉的操作規則。

1. **信任驗證堆疊，不信任生成器。** 判決只有在偵測器真的執行過、而且被證明還活著時才算數。被跳過的閘門不算通過。過去一直通過，不構成撤除強制的理由。
2. **強制優先於指引。** 只有閘門具有權威。
3. **一個模式只以四種形式存在**：準則、範本、禁則、閘門。缺任何一種就視為不存在。
4. **誤報絕不在生成的產物裡修。** 閘門錯了就修閘門；閘門對但律法錯了，就經由人類修訂律法。
5. **偵測成本決定回饋頻率。**
6. **建構者不得修訂律法。** 模型可以起草、甚至動手改，但永遠不能核准。
7. **機器驗證 S = P = T，人類判斷 S = W。**

另一個貫穿全文的要求：**每一道閘門都是確定性的程式，判決路徑上沒有語言模型。** 同一個產物每次得到不同判決，修復迴路就無法收斂。

## 四形式模式語言

讀者是不可信的建構者，所以每個模式要有四種互相耦合的形式：

| 形式 | 內容 |
|---|---|
| 準則（doctrine） | 文字說明何時適用、為何適用 |
| 範本（template） | 精確到匯入路徑的程式碼骨架，建構者只填領域內容 |
| 禁則（prohibition） | 不得出現什麼、不得缺少什麼。通常禁止的是該模式所取代的主流慣用法 |
| 閘門（gate） | 確定性的檢查器，附正反例夾具 |

兩點值得注意：

- 模式網路是選擇性的。團隊沒有約束用法的模式不放進來，建構者可以自由使用。因為建構者的一般能力和偏向來自同一個訓練來源，傳統只需要寫下模型的預設無法可靠提供的在地選擇。
- 不是每道閘門都是某個模式的第四形式。檢查「程式有沒有做到規格說的事」的閘門，依據是規格，屬於 S–P 或 S–T，不屬於模式語言。

## 問題側：問題框架

理論篇的規格依 Michael Jackson 的問題框架分類。每種框架類型帶有已知的關注點，等於一份可以重複使用的不適配清單，成本攤在同類的每一個問題上。需求則來自 Event Storming 工作坊。

框架類型用來分類問題，和架構無關。但文章明說：**問題的表徵是依架構而定的**，它用所選解法家族需要的詞彙來表達需求。綜述篇的說法是，規格刻意以主版繫結的詞彙撰寫；許多專案只需要一個繫結，中立的定義語言會讓規格寫起來比較不自然。中立的定義語言與 MGD 相容，但尚未測試。

## 主要脈絡與代理脈絡

| 類別 | 是什麼 | 例子 |
|---|---|---|
| 主要脈絡（經驗性） | 權威的來源，事實就是事實 | 編譯器接受什麼、執行環境怎麼運作 |
| 主要脈絡（裁決） | 由權威的宣告創造出來的要求。主要的是裁決這個行為，不是記錄它的文件 | 架構決策、利害關係人的裁決 |
| 代理脈絡 | 轉述主要脈絡的文件，權威是借來的 | 規格、模式文件、範本、規則目錄 |

代理會無聲地偏離來源。於是產物可能適配每一個代理，卻不適配主要脈絡，文章稱為**假綠燈**。

對策是核對（reconciliation）：主要脈絡能機械查詢時，直接拿代理和它比；不能時（例如裁決），指定一份代理當正本，其他副本和它比。副本彼此一致不代表和裁決一致。

## 漏網缺陷怎麼回應

每一個逃過閘門的缺陷，都必須用下列方式之一回應：

- 納入機械化的不適配清單：新增偵測器，或修復既有的偵測器、它的可達性、它讀取的代理。
- 修訂律法。
- 人類明確裁決：把這類缺陷放在清單之外，並指明改由什麼來涵蓋。這樣就沒有任何「機器已檢查」的主張建立在它上面。

守護「反主流」慣例的規則，不因為一段時間沒觸發就退役。只有在傳統或架構改變、它檢查的情境不存在時才退役。

## 什麼叫「足夠」

理論篇附錄 A 的定義：充分性是相對於主張的。harness 足夠的條件不是它建立了絕對的正確性，而是它履行了支持那個有界主張所需的每一項義務。那個主張是：「在這份律法之下，清單上的每一項不適配都不存在」。

附帶一個條件：要有證據顯示清單上的每一項都真的被評估了。只回報通過的判決、不回報有幾項沒評估到的 harness，宣稱的比它檢查的多。

詳見 `04-definition-of-enough.md`。

## 文章自己承認的限制

- **S–T 最弱。** 建構者把同一個誤解同時帶進程式和測試，兩者可以一起通過。mutation testing 幫不上忙：它衡量的是測試與程式的關係，測試可以拿到很高的分數，同時斷言的是錯的業務規則。
- **閘門全過，系統仍可能失敗。** 綜述篇記錄了兩種方式：互相衝突的規則，以及比規則更窄的驗收例子。
- **通過行為測試，也可能違反規則。**
- **harness 自己會失效。** 一道閘門曾悄悄跳過 62 個驗收場景。
- **人類權威建立的是問責，不是無誤。** 律法不一致的案例，起點是人寫下的規則。
- **只由人類核准規則，可能形成瓶頸。** 建立和維護律法與 harness 的成本沒有量測。
- **證據只來自一個專案**、同一位主要立法者。可移植性是尚未充分測試的預測。
- **不是什麼都值得這樣做。** 探索性原型、一次性工具、架構還在摸索的階段，這套做法買到的很少。參考實作自己的前端就沒有納入治理。
