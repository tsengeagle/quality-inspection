# 規格格式的決定

2026-11-15。本文件記錄規格格式 v1 的各項決定與理由。格式本身寫在 `specs/README.md`，那份是律法；本文件只是說明。

## 一、背景

負責人 2026-11-14 裁決：測試與規格要列為律法，但要等 `/specs` 的格式完整、問題側的規格穩定之後才生效（`09-law-inventory.md` 第三節）。所以先定格式。

格式以 `spec-draft/README.md` 的七條規則為起點。那份是 2026-11-11 為 ReviewProject 試作時寫的。

## 二、決定（2026-11-15，負責人照建議裁決）

| # | 題目 | 決定 | 理由 |
|---|---|---|---|
| 1 | 檔案格式 | YAML，CI 安裝固定版本的 PyYAML | 人要讀、要寫。TOML 寫巢狀規則太冗長；JSON 不適合手寫 |
| 2 | 檔案切分 | 每個 aggregate 一組檔案 | 和草稿一致；規則多了再拆 |
| 3 | 出處的寫法 | 結構化：`decision`、`design_decision`、`doc`、`example`、`scenario`、`rule` | 自由文字無法機械核對。試跑時發現 `DD-03` 會被誤認為 `D-03` |
| 4 | 錯誤代碼對應 HTTP 狀態碼 | 放在實作端的對應表，規格只寫分類 | 規格不出現實作詞彙 |
| 5 | `openspec/` | 移除 | 目前是空的；`openspec/specs` 容易和 `/specs` 混淆。另開 PR 處理，見第六節 |
| 6 | 沒有範例涵蓋的規則 | 先只列出，第 4 期之後改為擋下 | 現在擋下的話，ReviewProject 有 10 條規則沒有範例，會卡住升格 |

## 三、和草稿格式的差異

| 項目 | `spec-draft/README.md` | 格式 v1 |
|---|---|---|
| `spec_version` | `0.1-draft` | `1` |
| `source` | 自由文字或文字清單 | 結構化清單，每一項必須指向存在的東西 |
| `proposed` 規則 | `question` 指向題號 | 同，且題號必須是 `OPEN-QUESTIONS.md` 裡的標題 |
| 錯誤代碼分類 | 有，未限定 | 只能是 `denied`、`not_found`、`invalid_input`、`conflict`、`rule_violation` |
| 實作詞彙 | 人工檢查 | `specs/forbidden-vocabulary.txt` 機械比對 |
| 檢查程式 | 無 | `harness-core/spec_lint.py`，CI 的 `spec-check` 工作 |

## 四、對 ReviewProject 草稿的試跑（2026-11-15）

`spec-draft/` 以「只列出」模式檢查，結果：規則 36 條，問題 50 個。

| 問題 | 數量 | 處理 |
|---|---|---|
| `spec_version` 不是 1 | 3 | 升格時改 |
| 出處還是文字寫法 | 46 | 升格時改成結構化 |
| RP-PUB-01 的 `question` 是 Q-08，但 `OPEN-QUESTIONS.md` 沒有這個標題 | 1 | 實際問題，升格前要修 |

另外列出：10 條規則沒有範例涵蓋；1 個範例的 `basis` 含 `proposed` 規則（RP-PUB-01）。

### Codex 審查後的修正（PR #19）

| 發現 | 原本的行為 | 修正 | 新的測試 |
|---|---|---|---|
| 正式規格可以引用只存在於草稿的規則 | `--report-only` 的草稿規則也算進可引用的 id，正式規格的 `source` 或範例的 `basis` 指向草稿規則仍然通過 | 擋下的規格只用擋下的規格的 id 核對；草稿仍可引用兩者 | 3 個 |
| `observe` 的步驟沒有檢查 | 只檢查 `given` 與 `when`；拼錯或沒列在 `needs` 的查詢會通過 | `observe` 和其他步驟一樣核對 use case 與 fixture | 2 個 |

### Copilot 審查後的修正（PR #19）

Copilot 審的是 `cfd848a`，7 點中 2 點與上表重複，其餘 5 點：

| 發現 | 原本的行為 | 修正 | 新的測試 |
|---|---|---|---|
| 專案路徑寫死在 `harness-core/` 裡 | 裁決紀錄、設計文件、測試文件的位置寫死成本專案的路徑，違反 `harness-core/README.md` 規則 1 | 裁決紀錄讀清冊的 `@decision-log`；另外兩個目錄由 `--design-docs`、`--testing-docs` 傳入，沒設定時用到的出處算問題。不新增清冊指示，因為 `law_check.py` 會把不認得的指示判為無法評估 | 3 個 |
| 缺少 `forbidden-vocabulary.txt` 時直接通過 | 禁用詞彙清單是空的，等於沒檢查 | 判定無法評估 | 1 個 |
| 非字串的 `id` 被略過 | `id: 123` 不算規則，什麼都不檢查 | 記成問題 | 1 個 |
| 前置檢查與 use case 規則可以沒有 `outcome` | 刪掉 `outcome` 就跳過結果與錯誤代碼的檢查 | 這兩類必須有；不變量、轉移、成功狀態維持隱含的結果 | 1 個 |
| 型別不合法的值讓程式中止 | `fixtures: [draft]` 之類會丟出例外，草稿的問題也會讓 CI 失敗 | 逐項檢查型別並記成問題；另加保險，沒預料到的型別錯誤記成「檢查沒有做完」，擋下的規格因此未通過 | 1 個（14 種寫法 × 擋下／只列出） |
| 跨 aggregate 的 `basis` | `proposed` 的提示與涵蓋只看自己的 aggregate | 兩者都跨 aggregate 計算；擋下的規則只算擋下的範例 | 1 個 |

新的 8 個測試對修正前的程式（只改成相同的路徑與呼叫方式）全部失敗。

## 五、對外部資源協定的試寫（2026-11-19）

### 目的

格式 v1 只用在兩個業務 aggregate（ReviewProject、ScoreSheet）上。這次用一份性質不同的問題試寫，看 v1 的極限在哪裡。

試寫的對象是負責人提供的便利貼白板「同機共用醫事人員卡｜目標流程（提案，尚未實作）」。白板描述兩件事：同一台電腦的多個行程怎麼輪流使用一張醫事人員卡（用一次卡；批次簽章），以及每一種失敗的結果。白板的核心是三條規則：

1. 先取得鎖，才能開啟卡片模組。
2. 卡片模組確認關閉之後，才能放鎖。
3. 對方可能還持著卡時，不送 PIN。

另外，白板把「拿到簽章」和「卡片資源可以交給對方」當成兩件事，分開看。

這個問題不屬於本專案：repo 裡沒有相關的文件或程式，也不在 `law/coverage.txt` 的問題側。草稿只放在 session 的暫存目錄，沒有進 repo。

### 做法

1. **嚴格版**：只用 v1 有定義的欄位。白板沒有任何裁決，所以規則全部是 `proposed`，題目寫在 `OPEN-QUESTIONS.md`。
2. **擴充版**：在嚴格版上，把 v1 表達不了的東西用最自然的寫法硬寫進去。這也是 AI 起草時最可能出現的寫法。

兩版都放在 `--specs` 的位置跑 `spec_lint.py`，也就是擋下模式。執行器沒有實際跑，因為沒有對應的 use case 程式；執行器的行為依 `acceptance/ExampleRunner.java` 的原始碼判斷。

### 結果一：嚴格版通過，但範例是空的

- 規則 17 條，問題 0 個，結束代碼 0。
- 4 個範例都因為 basis 含 `proposed` 規則而被列出。
- 8 條規則沒有範例涵蓋，包括規則 1、2，以及整個批次簽章。

通過本身就是問題。v1 寫不出「另一個行程持著鎖」「讀到的卡號不符」「關閉模組失敗三次」這些前提，所以範例只剩下結論。成功的範例和被拒絕的範例，`given` 與 `when` 一字不差，`then` 卻不同，`spec_lint` 沒有發現。

| 白板的內容 | v1 寫得出來嗎 |
|---|---|
| 角色、命令 | 可以：`actors`、`usecases` |
| 等不到鎖、鎖檔無法建立、卡號不符、模組回錯誤碼 | 可以寫成 guard 或規則加上錯誤代碼，但前提無法在範例裡建立 |
| 「卡片資源異常」的狀態 | 勉強可以：把卡片資源當成 aggregate，寫狀態與轉移 |
| 待釐清的風險（記憶體、整批持鎖超過 15 秒、分段的 K） | 可以：`proposed` 加題目 |
| 規則 1 到 3（呼叫的順序、不送 PIN） | 只能寫成文字的不變量，沒有東西驗證 |
| 兩個面向的結果（簽章已取得，但鎖沒有釋放） | 不行：每條規則只有一個結果（第三節規則 4） |
| 外部失敗（DLL 錯誤碼、關閉失敗三次、第 N 份簽章失敗、第 M 份保存失敗） | 不行：範例只能用 use case 準備資料 |
| 時間（最多等 15 秒、對方逾時） | 不行：範例無法固定時鐘 |
| 並行（兩個行程搶同一把鎖） | 不行：範例是單一操作者、依序執行 |
| 次數（重試三次、PIN 類錯誤不重試） | 不行：範例無法計算對外部的呼叫次數 |
| 被拒絕時帶資料（顯示佔用者） | 不行：`REJECTED` 只比對錯誤代碼 |

### 結果二：硬寫進去的東西，8 項只擋下 1 項

| 硬寫進去的寫法 | `spec_lint` | 執行器 |
|---|---|---|
| 一條規則有兩個結果：`outcome: [ {SUCCESS…}, {REJECTED…} ]` | 擋下 | — |
| 第二個面向：`outcome: { result: SUCCESS, resource: FAULTED }` | 沒發現 | `then` 只讀 `result` 與 `code`，其餘的鍵忽略 |
| 呼叫的順序與次數：`then` 裡的 `calls`、`not_called: [sendPin]`、`call_count` | 沒發現 | 忽略 |
| 被拒絕時帶資料：`REJECTED` 加 `output: { holder }` | 沒發現 | 忽略 |
| 外部的替身：`given` 的步驟寫 `{ port: CardModule, on: closeModule, fail_times: 3 }` | 沒發現：步驟只檢查 `run` 與 `use` | 沒有 `run` 的步驟丟出 `RunnerProblem`，範例未通過 |
| 第二個行程：`given` 的步驟寫 `{ process: other, holds: lock }` | 沒發現 | 同上，未通過 |
| 固定時鐘：`given` 的步驟寫 `{ clock: { advance: 15s } }` | 沒發現 | 同上，未通過 |
| 實作詞彙：InitModule、CloseModule、HCAAPI、DLL、XML、JVM | 沒發現 | — |

### 發現

1. **v1 會靜默接受它不認得的欄位。** 這是最大的風險。`then` 與 `outcome` 裡多出來的鍵，`spec_lint` 與執行器都不理，結果是通過。讀規格的人會以為 `not_called: [sendPin]` 已經驗證過，實際上沒有任何東西檢查它。這違反第三節的前提，也違反 P1 的原則：沒有評估的檢查不能算通過。`given` 的步驟會在執行器那裡失敗，不會假裝通過，但 `spec_lint` 仍然放行。
2. **`spec_lint` 只檢查引用，不檢查範例能不能分辨情境。** 兩個 `given` 與 `when` 完全相同、`then` 不同的範例，不可能同時通過，但 `spec_lint` 看不出來。
3. **禁用詞彙是針對本專案的技術棧寫的。** `forbidden-vocabulary.txt` 只列 HTTP、Spring、JPA、資料表之類的詞。裝置、外部協定、執行環境的詞都抓不到。第三節規則 6 字面上禁止，機器不擋。換成別的專案或別的問題，清單要重寫。
4. **v1 適合「條件加結果」的業務規則，不適合外部資源的協定。** 協定的不適配出在呼叫的順序、資源有沒有交出去、部分成功，這三種 v1 都沒有寫法。

### 格式 v2 的候選

| # | 項目 | 回應的發現 | 備註 |
|---|---|---|---|
| 1 | 封閉的結構：`spec_lint` 與執行器把未定義的欄位判為問題 | 1 | 和 HTTP 契約的形狀一樣採封閉物件（`specs/README.md` 第七節）。不論要不要支援協定，都值得先做 |
| 2 | 偵測 `given` 與 `when` 相同、`then` 不同的範例 | 2 | 確定性的比對即可 |
| 3 | 多個面向的結果，例如 `outcome` 分成 `signature` 與 `resource` | — | 要先裁決第三節規則 4 是否放寬 |
| 4 | 外部埠的宣告，以及範例裡的失敗注入 | — | 執行器要有替身的機制 |
| 5 | 對外部呼叫的順序、次數、未呼叫的斷言 | — | 依賴第 4 項 |
| 6 | 可以固定的時鐘 | — | 已知缺口；ReviewCase 也會用到 |
| 7 | 並行的範例（兩個操作者或兩個行程） | — | 成本最高，最後考慮 |
| 8 | 禁用詞彙的清單依專案或問題的類型分開 | 3 | 和 `harness-core/` 拆成獨立 repo 的工作一起考慮 |

第 1、2 項是現行 v1 的漏洞，和協定無關。第 3 到 7 項是協定類問題才需要的擴充，其中第 6 項 ReviewCase 立法時也會碰到。

## 六、還沒做的

- 移除 `openspec/`。牽涉 `.claude/commands/opsx/` 與 `.claude/skills/openspec-*`，它們是律法，而 `openspec/` 本身不是；同一個修法 PR 不能夾帶非律法的修改，所以要分兩個 PR。
- 第三節規則 8（架構詞彙只用 `glossary.md` 有定義的詞）還沒有機械檢查。
- 第五節的 v2 候選第 1、2 項（未定義的欄位判為問題；偵測分辨不了情境的範例）已由 D-063（格式 v1.1，2026-11-20）在 `spec_lint` 實作。執行器沒有改，它仍然忽略不認得的鍵；靠 CI 的 `spec-check` 擋住，合併進來的規格才不會有未定義的欄位。
- ReviewProject 已升格（2026-11-15）：出處改成結構化、補了 13 個範例、RP-PUB-01 與 RP-UPD-S3 依 D-049 裁決。升格條件第 3 項「負責人逐條讀過」由升格 PR 的核准簽章承擔。
