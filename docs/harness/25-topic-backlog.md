## 待辦（依序）

1. **建構不得先於它依據的裁決併入主線**（負責人 2026-11-26 列入，排在最前）：現在沒有閘門把建構 PR 綁到「它依據的裁決已經生效」。建構 PR 只要不碰律法路徑、改的是已立法的檔案，`law-check` 就判為建構 PR 而通過，不管它依據的修法 PR 有沒有簽章合併；到目前為止靠的是「修法在前、建構在後」的順序紀律。
   - 發現的經過：D-096 的修法 PR #194 等簽章時先做了建構（#195）。#195 被擋下，是因為它的分支刻意疊在 #194 的分支上，對 `main` 的差異帶著未簽章的律法修改（本機 `law_check`：分類為修法 PR，夾帶程式、沒有簽章）。同樣的修改如果從 `main` 開分支，不會被擋。
   - 擋得到的情況：建構需要先改律法才會綠（規格的範例凍結在 `known-test-failures.txt`、新檔案要先登記進 `coverage.txt`、HTTP 契約要先改）。擋不到的是「行為不變、不需要新規格」的建構，以及搶在規格之前改行為但沒有範例會紅的建構。
   - 要裁決的：要不要擋；怎麼表達建構依據哪一個裁決（例如提交訊息或 PR 帶裁決編號，由 `law-check` 檢查該編號已在 base 的 `decision-log.md`）；沒有對應裁決的建構（純重構、修缺陷）怎麼處理。草稿 `46-build-after-ruling-draft.md`（B-1～B-8），待裁決。
2. **母體來源的介接**（D-086 第 1、2、6 點延後的部分）：抽選失敗怎麼記錄（`FAILED`、`SamplingBatchFailed`）、重跑的成功路徑（D-013）、抽樣比例與排除條件。要等真正的母體來源定案。
