> 本文件只記錄實測的結果與發現，沒有修改程式。不是律法，也不是裁決；每一項怎麼處理由負責人決定。
> 發現的編號 X-01～X-13 只在本文件使用。

## 一、做了什麼

把 `main`（`02811a3`）的後端與前端都在本機跑起來，用瀏覽器（Playwright）以各種角色操作每一頁，從抽選走到結案，再看報表與匯出。前端沒有畫面的步驟改成直接打 API。

| 項目 | 內容 |
|---|---|
| 後端 | `./gradlew bootRun`，`local` profile，H2 記憶體資料庫，JDK 17 |
| 前端 | `ng serve --configuration=standalone` |
| 角色 | `HOSPITAL_MANAGER`、`REVIEWER`、`REREVIEWER`、`AUDITOR`、`SYSTEM_ADMIN`，都在院區 `H001` |
| 資料 | 後端啟動時的種子資料（`PROJECT-001`、3 筆案件），加上這次經由 HTTP 建立的一個專案、一份評分表（2 節 3 題，都是 `FIXED`、必答）、抽選出來的 20 筆案件 |
| 工具 | `docs/review/tools-2026-11-28/`，用法見第六節 |

### 角色是怎麼切換的（重要的限制）

standalone 模式的操作者寫死成 `HOSPITAL_MANAGER`，proxy 帶的 `api-key` 也是固定的。這次的作法：

1. **暫時修改** `standalone-mock-actor-context.source.ts`，讓它從 `localStorage` 讀操作者（`tools-2026-11-28/standalone-actor-switch.patch`）。**這個修改沒有提交，測完已還原。**
2. Playwright 攔下前端送往 `/api/quality-inspection/**` 的請求，改送到後端並換上對應身分的 `api-key`。沒有經過 `proxy.conf.js`。

所以這次測的是「前端的程式 + 真實的後端」，不是 hosted（shell）模式，也不是正式的登入流程。

### 這次確認是「設計如此」的

容易被誤認成缺陷，記下來避免之後重查：

- 匯出時，還沒有進入複審中、結案、取消的案件，兩個分數顯示「已遮罩」。這是 RC-RPT-08（之後還可能指派複審醫師）。
- 三題作答 30、20、25，總分是 100。`FIXED` 題型的分數是滿分 × 權重，與作答的值無關（`specs/review-case/model.yaml`）。
- 複審醫師讀到的初審提交沒有分數與評語（RC-VIS-02）。

### 已知的缺陷，這次在畫面上也看到

- E-10、E-11（`SYSTEM_ADMIN` 的案件列表與匯出比白名單多）：列表對系統管理者顯示「來源案件」「病歷類型」，匯出有「專案」欄。修正在 #215。
- 狀態在多數頁面顯示代碼而不是中文名稱；案件詳情的頁首把狀態顯示兩次（#208 已記）。

## 五、建議的處理順序

只是建議。

1. **X-01 要先裁決。** 醫師怎麼拿到題目，是後端契約的問題。它要修法，而且沒有它 X-02 做不出來。**已起草**：`docs/harness/52-reviewer-score-sheet-items-draft.md`（R-1～R-8，待裁決）。查證後的原因：D-050 第 7 點、D-051 都寫明醫師「審查時用案件的 snapshot」，但 snapshot 沒有實作，D-094 又裁決不做；這個假設落空之後沒有人回頭補。草稿建議新增一支以案件為範圍的查詢。
2. **X-02、X-03** 是同一件事的兩半：作業頁的題目區。要先寫頁面規格（題目怎麼呈現、唯讀時怎麼呈現）。這是目前離「系統可以用」最遠的地方。
3. **X-04** 先決定五個命令各自放在哪一頁，再排進頁面的工作。
4. **X-05、X-06、X-07、X-09、X-10** 是純前端的小修，不需要簽章。X-05 是展示時第一眼就會遇到的。
5. **X-08、X-11、X-12、X-13** 先由負責人判斷是不是缺陷。

這 13 項都是讓人操作才找到的，現有的閘門一項都擋不到：前端的 E2E 用的是自己寫的假回應（漏網紀錄 E-04、E-05 指出的同一個弱點）。對應的是 D-099 的批 5「打真實後端的 E2E」，還沒有起草；這次的腳本可以當起點。

## 六、怎麼重跑

工具在 `docs/review/tools-2026-11-28/`：

| 檔案 | 用途 |
|---|---|
| `lib.js` | 開一個指定角色的瀏覽器分頁，攔下 API 請求改送後端、換上那個角色的 `api-key`，記下每個回應與主控台的錯誤 |
| `steps.js` | 讀一份步驟的 JSON（角色、起始網址、點擊與填寫），每一步之後印出網址、API 回應、畫面文字、按鈕、輸入框 |
| `api.py` | 直接打後端的小工具，用來建立資料 |
| `standalone-actor-switch.patch` | 讓 standalone 模式的操作者可以由 `localStorage` 指定的暫時修改。**只在本機套用，不要提交** |

```bash
# 1. 後端（JDK 17）
cd services/quality-inspection-service && ./gradlew bootRun

# 2. 前端：先套用暫時的修改，測完用 git checkout 還原
cd frontends/quality-inspection-frontend
git apply ../../docs/review/tools-2026-11-28/standalone-actor-switch.patch
npx ng serve --configuration=standalone --port 4200

# 3. 步驟檔的例子：以初審醫師開我的佇列
echo '[{"role":"REVIEWER","uid":"reviewer-1","goto":"/cases","acts":[]}]' > steps.json
node docs/review/tools-2026-11-28/steps.js steps.json
```

這些腳本是探索用的，沒有斷言，不會自己判斷對錯；每一步的輸出要人讀。步驟檔沒有收進來，因為裡面是這次執行產生的 id。`api-key` 只解碼、不驗簽（由 gateway 驗），所以本機可以自己組。
