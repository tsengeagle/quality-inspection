## 1. 摘要

iccard localserver 與 HCAAPI localserver 會在同一台電腦上，用全景的 `HCAPKCS11.dll` 對同一張醫事人員卡簽章。在一組卡片、讀卡機與 DLL 版本上的實驗觀察到：

- 一方登入中，另一方登入失敗，其中一個方向回報的錯誤碼是 **9039「PIN 碼錯誤」**。
- 一方關閉 Module 之後，另一方握著的 Session 下一次簽章失敗。

本設計提出一把兩支程式共同遵守的跨行程檔案鎖，規則是「沒有持鎖就不得開啟 Module，Module 沒有確認關閉就不得放鎖」。為此 HCAAPI 必須從「握住 Session 直到前端關閉」改為「每個指令自開自關」。

取鎖、開關、清理這一段做成一個共用元件，先在 iccard 開發與驗證，再以 jar 的形式交給 HCAAPI 引用。

## 2. 背景

### 2.1 兩支程式用卡的方式

兩支程式的使用者都是該台電腦的操作者本人，沒有多人多連線的情境。用卡都由使用者操作觸發，沒有排程。

| | iccard localserver | HCAAPI localserver |
|---|---|---|
| 用途 | 電子處方箋簽章 | 電子病歷簽章 |
| 觸發 | 醫師開立處方 | 醫師在 UI 按「開始簽章」，UI 之後定期呼叫 HCAAPI |
| 廠商 jar 版本 | 1,0,12,410 | 1,0,10,1208 |
| 用卡方式 | 每次操作自開自關，約 2.7 秒 | `initialize` 開啟後握住，直到前端送 `closeModule` |
| 入口 | `HcaServiceImpl` 四個方法 | `HCAUtils.callAPI` 各指令 |
| 行程內序列化 | 無 | 無；每條連線一個執行緒，狀態全在 static 欄位 |

iccard 的觸發點：

- 開立處方：`ICCardServer.executeLegacyErxQrJson` → `QrCodeOrchestrator.generateQrCodes` → `HcaServiceImpl.getSignnatureAndCertSerial`
- 驗卡與 PIN：`SigningContextManager.prepareAndValidatePhysical` → `HcaPhysicalCardVerifier` → `getCertificateSerial` 與 `getCardInfo`（連續兩輪開關）
- 調劑端 `verifySignature` 只用憑證驗章，不碰卡。

HCAAPI 的觸發點（socket 60002 → `HcaApiServer.callAPI` → `HCAUtils.callAPI`）：

| 指令 | 對卡的動作 |
|---|---|
| `initialize` | 關閉既有 → 開 Module、Session、取公私鑰，之後不關 |
| `makeSignature` | 用既有 Session 逐份雜湊與簽章；迴圈內每份文件還有時戳查詢、FTP 上傳與確認、資料庫回寫 |
| `updateCardinfo`、`specialUpdateCardinfo` | 重開 Module 與 Session，之後不關 |
| `checkHCAAPI` | 先關閉自己已開的 Module，再開 Module 讀卡片資料後關閉，不登入 |
| `closeModule` | 關閉 Session 與 Module |
| `verifySignatureByCert*`、`verifyTS` | 不需要 Module |

socket 指令本身不帶 Module 或 Session 的 handle。前端只依賴「先 `initialize` 再 `makeSignature`」的順序，不依賴 DLL 的 Session 是否一直開著。

### 2.2 已完成的前置修正

廠商 jar 會把 `HCAPKCS11.dll`、`HCAAPIJNI.dll` 以固定檔名解到 `%TEMP%` 再載入，造成後啟動的程式無法初始化。iccard 已改為解到 `%TEMP%\iccard-localserver-hca\`（`HcaNativeBootstrap`），實機確認兩支程式可以任意順序啟動。該修正只解決檔案衝突，與本文的卡片互斥是兩件事。

## 3. 實驗證據

使用兩個 repo 的 POC（各自掛自己的廠商 jar），同一台讀卡機、同一張卡、相同 PIN，2026-11-19 共三輪。每筆成功的簽章都以卡上憑證用純 Java（`SHA1withRSA`）驗章。

### 3.1 第一輪：iccard 連續簽章中，HCAAPI 加入

| HCAAPI 端動作 | 當下 iccard 端 | 結果 |
|---|---|---|
| InitModule | 已登入、讀憑證中 | 成功 |
| InitSession | 已登入、簽章中 | 等 963 ms 後回 9062「已登入裝置」 |
| InitSession（同一個 Module 重試） | 關閉中或重開中 | 一律回 9046「指定的連線不存在」 |

iccard 端 14 筆全部成功且驗章有效，每筆約 2.67 秒，不受影響。

### 3.2 第二、三輪：HCAAPI 握住 Session，iccard 嘗試

第三輪把動作拆開，因果較清楚：

| 順序 | 程式 | 動作 | 結果 |
|---|---|---|---|
| 1 | HCAAPI | InitModule、InitSession、讀憑證 | 成功，握住 |
| 2 | iccard | InitModule | 成功 |
| 3 | iccard | InitSession | **9039「PIN 碼錯誤」**（PIN 確認無誤，第二輪也是 9039） |
| 4 | HCAAPI | 取金鑰、簽一次 | 成功 |
| 5 | iccard | CloseModule | 成功，耗時 1008 ms（平常約 200 ms） |
| 6 | HCAAPI | 再簽一次 | **9016「裝置錯誤」** |
| 7 | iccard | 單獨完整跑一次 | 全部成功 |

### 3.3 觀察

以下都是「在這組卡片、讀卡機與 DLL 版本上觀察到」，不是元件的保證行為。

| 編號 | 觀察 | 依據與次數 |
|---|---|---|
| F1 | 兩個行程可以同時開啟 Module | 三輪的 InitModule 都成功 |
| F2 | 一方登入中，另一方登入失敗，兩個方向都觀察到 | HCAAPI 去試回 9062（一次）；iccard 去試回 9039（兩次） |
| F3 | 登入失敗之後，對方仍能簽章 | 第三輪步驟 4（一次） |
| F4 | 一方 CloseModule 之後，另一方下一次簽章失敗 | 第三輪步驟 5、6（拆開步驟的只有這一次；第二輪結果一致但步驟未拆開） |
| F5 | 登入失敗後，同一個 Module 之後的登入都回 9046，需重開 | 第一輪連續三次 |
| F6 | 有一次跨行程呼叫等待了 963 ms 才回錯誤 | 第一輪（一次）。不能據此認定元件有安全的排隊機制 |
| F7 | 沒有觀察到元件回報成功但驗章失敗的簽章 | 三輪所有成功簽章 |

### 3.4 證據的限制

- 只在一台電腦、一台讀卡機、一張卡上做過。
- **9039 是否真的扣掉卡片的 PIN 錯誤次數，未知。** 驗證需要連續失敗三次，有鎖卡風險，沒有做。本設計一律當成會扣，不在競爭時送 PIN，也不為了查證而重試。
- F2 兩個方向錯誤碼不同，推測是兩邊 DLL 版本不同所致，未驗證。
- F4 的成因未知。CloseModule 耗時為平常五倍，可能是對卡片做了重置，但沒有證據。
- F7 的樣本有限：兩邊從未真的同時簽章成功過，因為其中一方總是登入失敗。
- 行程在持卡時異常結束後，卡片停在什麼狀態，沒有測過。

## 4. 現況的風險

| 情境 | 觀察到或預期的後果 |
|---|---|
| 醫師在 HCAAPI 簽章期間（已 `initialize`、未 `closeModule`）開立電子處方 | iccard 登入失敗（觀察到 9039）；每次失敗是否扣 PIN 次數未知，若會扣則連續三次鎖卡 |
| iccard 簽章的約 2 秒內，HCAAPI 剛好執行 `initialize` | HCAAPI 登入失敗（觀察到 9062） |
| iccard 簽章中，HCAAPI 執行 `checkHCAAPI`（會開關 Module） | 依 F4 推論，iccard 進行中的 Session 可能失效；這個組合沒有直接測過 |
| iccard 任一步驟失敗 | 現行程式直接拋例外，不關 Session 與 Module |
| iccard 清理時拋例外 | 已取得的有效簽章被丟棄（`HcaServiceImpl.java:82`） |
| HCAAPI 的 `CloseSession` 或 `CloseModule` 回錯誤 | handle 只在回傳 0 時清零。殘留的 Session handle 會讓下一次 `initialize` 改走「關 Session」而不登入，之後持續失敗 |

## 5. 設計目標

- 任何時刻只有一個行程開著 Module。
- 絕不在對方持卡時送出 PIN。
- 行程異常結束不會留下死鎖。
- 取得簽章與資源清理是兩件事：清理失敗不丟棄已取得的簽章。
- HCAAPI 對前端的 socket 指令格式不變。行為上的差異列在 §6.7。

不在本次範圍：

- HCAAPI 的 `NHI` 讀卡機模式（走 `HCACSAPI` 與健保讀卡機 COM 埠）。
- iccard 的 `HCA_CLI` 簽章模式（已不使用）。
- 其他廠商或工具對同一張卡的使用；它們不認得這把鎖。

## 6. 設計

### 6.1 規則

> 1. 必須先取得鎖才能呼叫 `InitModule`。
> 2. `CloseModule` 確認成功後才能釋放鎖。
> 3. 持鎖的意思是「本行程可能還有 Module 開著」。

鎖的範圍包住整段 `InitModule → CloseModule`，不只是登入到登出，因為 F4 顯示關 Module 就可能影響對方。不需要 Module 的操作（純憑證驗章、時戳查詢與驗證）不取鎖。

規則 2 與 3 的結果：

- 對方能取得鎖，就代表持鎖方已確認關閉 Module，或行程已經結束（Module 隨行程消失，作業系統同時釋放檔案鎖）。兩種情況都不需要另外的共享狀態來表示「設備暫停」。
- 取得鎖不等於設備健康。卡片被拔掉、換掉或讀卡機異常，由取鎖之後的讀卡號步驟發現（§6.3、§6.5）。
- 行程異常結束後卡片是否停在已登入狀態，是鎖無法表達的，列為待驗證（§8）。

### 6.2 鎖的規格

| 項目 | 規格 |
|---|---|
| 機制 | `java.nio.channels.FileChannel.tryLock()`，鎖整個檔案 |
| 檔案 | `C:\opdsysora\newHis\hca-card.lock` |
| 行程內 | 檔案鎖以整個 JVM 為單位，前面再加一把 `ReentrantLock`，同時提供行程內序列化。正常情況下取鎖與放鎖在同一個執行緒、同一個指令內完成，不跨指令持有；卡片資源異常時，檔案鎖保留到復原或行程結束，`ReentrantLock` 仍在該指令結束時釋放 |
| 取得方式 | 先在期限內取得 `ReentrantLock`，再每 100 ms 輪詢 `tryLock()` 直到期限 |
| 等待上限 | 兩邊可以不同。iccard 要等 HCAAPI 的批次，建議 15 秒；HCAAPI 只需等 iccard 的一次用卡（約 3 秒），建議 6 秒左右（見 §10 待決 A） |
| 等待逾時 | 本次不呼叫 DLL，回報「卡片使用中」。不強制取鎖 |
| 正常釋放 | `CloseModule` 回傳成功後，在 `finally` 中釋放檔案鎖與 `ReentrantLock` |
| 清理失敗 | 見 §6.3，檔案鎖不釋放 |
| 行程當掉 | 作業系統自動釋放檔案鎖 |
| 鎖檔無法建立或開啟 | **拒絕操作**，回報明確錯誤，不得照常簽章 |
| 診斷資訊 | 持鎖時把程式名稱與時間寫到 `hca-card.lock.owner`。只用來在逾時訊息中顯示是誰佔用，寫入失敗不影響鎖，也不作為放行依據 |

實作上要注意的兩件事：

- 檔案鎖跟著 `FileChannel` 走，關閉 channel 鎖就放掉。卡片資源異常時要保留鎖，就必須把 channel 與 `FileLock` 留在元件的欄位裡不關閉；正常路徑才在放鎖時關閉。
- 同一個 JVM 已經持有這個檔案的鎖時，再呼叫 `tryLock()` 會拋 `OverlappingFileLockException`，不是回傳 null。輪詢取鎖與 `tryRecover` 都要先看元件自己的狀態，已持有就不再呼叫；並且仍要接住這個例外，當成「本行程已持有」處理。

選擇這個目錄的理由：兩個專案原本就使用 `C:\opdsysora\newHis\`，且它是機器層級的路徑，不受登入使用者的 `%TEMP%` 不同影響。

鎖檔失敗時拒絕操作的理由：照常簽章等於回到第 4 節的現況。

鎖與 §6.3 的流程由同一個共用元件實作，兩支程式引用同一個 jar，見 §6.8。

### 6.3 用卡流程與清理（兩邊共用）

```
取鎖
  InitModule
  讀卡號，與預期的卡號比對        ← 不需要 PIN；不符就不送 PIN
  InitSession（送 PIN）
  操作（讀憑證、取金鑰、雜湊、簽章）
  finally:
    CloseSession    ← 檢查回傳碼並記錄；失敗不跳過下一步
    CloseModule     ← 檢查回傳碼
放鎖（只有 CloseModule 確認成功時）
```

清理結果的處理：

| 情況 | 處理 |
|---|---|
| `CloseSession` 失敗、`CloseModule` 成功 | 視為已清理，記錄錯誤碼，正常放鎖；回給呼叫端的結果不受影響。前提是關閉 Module 會一併結束其下的 Session；這是假設。假的 DLL 只能證明流程有呼叫 `CloseModule`，證明不了這個假設，要以 §9 第 3 項的實機測試確認 |
| `CloseModule` 失敗 | 間隔短暫時間重試，最多三次 |
| 重試後仍失敗 | 本行程進入「卡片資源異常」狀態：檔案鎖不釋放，行程內的 `ReentrantLock` 照常釋放。之後每次用卡前先再試一次關閉，成功就恢復正常；仍失敗就拒絕用卡，提示使用者重新啟動該程式。對方看到的是等待逾時，訊息中顯示佔用者 |
| 操作已取得有效簽章，之後清理失敗 | 簽章照常回傳給呼叫端，不重簽。資源異常另外記錄，並依上一列處理 |
| 操作回傳錯誤碼 | 仍執行完整清理，再回報錯誤。元件對任何 DLL 錯誤碼都不自動重試，要不要再試由使用者決定；唯一的重試是關 Module |
| 卡號不符或操作失敗之後，關 Module 也失敗 | 原本的結果（卡片不符、用卡失敗）照常回報；本行程另外進入「卡片資源異常」，處理方式同上 |

卡片簽章是同步呼叫，結果不是簽章值就是錯誤碼，沒有「送出後結果不明」的狀態；對同一份資料重簽也沒有副作用。需要注意重複執行的是簽章之後的保存動作（HCAAPI 的時戳、FTP、資料庫），見 §6.6。

### 6.4 iccard localserver 的修改

- 新增共用元件（§6.8），包含鎖與 §6.3 的流程。
- `HcaServiceImpl` 的 `signData`、`getCertificateSerial`、`getSignnatureAndCertSerial`、`getCardInfo` 改走共用流程。錯誤路徑漏關、回傳碼未檢查、清理例外丟棄簽章三個問題一併修正。
- 驗卡流程（取憑證序號加取卡片資料）合併為一次持鎖、一次開關。
- `verifySignature` 不變。
- 等不到鎖：拋 `SignatureException`「醫事人員卡正由其他程式使用中，請稍後再試」。由使用者決定是否重試，程式不自動重試。
- 鎖檔失敗：拋 `SignatureException`「無法建立醫事卡互斥鎖，請聯絡資訊室」。
- 遇到 9039 就停（已決議，§10 第 11 項；以卡號比對為條件，兩者一起上版）：開處方時用的 PIN 已在驗卡時驗證過。若卡號相符而登入仍回 9039，最可能的原因是卡片被不守鎖的程式佔用（舊版 HCAAPI 或第三方程式），不是 PIN 錯。此時撤銷簽章情境、清除記住的 PIN，回報「卡片可能被其他程式佔用，請先結束電子病歷簽章」，醫師必須重新驗卡才能再簽。效果是把「每開一張處方送一次 PIN」降為「每重新驗卡一次送一次 PIN」。它只降低風險，不能消除；驗卡當下的 9039 仍然無法分辨是 PIN 錯還是被佔用。這一項與卡號比對都不依賴互斥，是否作為一包先於互斥上版，併入待決 K。
- 驗卡時的 9039：此時 PIN 尚未驗證過，無法分辨是打錯還是卡片被佔用。訊息必須兩種可能都說明，例如「PIN 碼錯誤，或醫事人員卡正被電子病歷簽章使用。請先結束電子病歷簽章；若確定 PIN 無誤，請不要重複輸入」。不能只顯示一般的 PIN 錯誤，否則醫師會以為自己打錯而重打。
- 9043（卡片已鎖）要單獨處理，不能和其他 PIN 類錯誤共用一般的失敗訊息。它是混版風險的最壞結果，醫師需要知道的是卡已經鎖了、不要再試、要走解鎖流程。驗卡與開處方時都可能遇到；遇到時撤銷簽章情境。HCAAPI 現有的訊息是請醫師把卡送人事行政課處理，iccard 的訊息應與院內實際的解鎖流程一致。
- 驗卡與開處方兩處 9039 提示文字中的「結束電子病歷簽章」是否真的會讓舊版 HCAAPI 放掉卡，尚未確認：舊版只有收到 `closeModule` 才關閉 Session，前端結束簽章時是否送出這個指令不在這兩個 repo 內（待決 N）。若不會，提示要改為關閉電子病歷簽章程式，因為行程結束一定會放掉卡。
- 卡號比對：iccard 現在每張處方都用記住的 PIN 登入，沒有比對卡號。簽章情境裡記的是憑證序號，但憑證要登入後才讀得到，不能用來決定要不要送 PIN。驗卡時加記卡號，簽章前比對，不符就要求重新驗卡。已決議納入（§10 第 10 項）。
- 簽章情境的期限是既有行為（`SigningContextManager`）：實體卡簽章情境帶有到期時間，到期時撤銷並清除 PIN，之後開處方會回「尚未設定電子處方箋簽章方式」。這發生在取鎖之前，本設計不改；它與「卡片不符」是不同的結果。
- 簽章取得後，iccard 自己用簽章值產生 QR Code（加密、拆分、產生影像）再回傳給呼叫端。這一段不碰卡，在放鎖之後執行；iccard 本機不寫入任何業務狀態。

預期持鎖時間：單張處方約 2.7 秒（實測 InitModule 0.57、InitSession 0.08、讀憑證 0.76、取金鑰 0.04、簽章 1.05、CloseModule 0.2），加上讀卡號的時間。

### 6.5 HCAAPI localserver 的修改

只在 `cardReader` 不是 `NHI` 時套用。用卡一律透過共用元件（§6.8），`HCAUtils` 內自行管理 handle 的 `initModule`、`initSession`、`closeSession`、`closeModule`、`getKey` 不再直接呼叫 DLL。

**`callAPI` 整體序列化（第一版前提）。** `HCAUtils` 的回傳結果（`returnMap`）、資料庫連線、PIN、使用者代號全部是 static 欄位，沒有任何同步。兩個指令若同時執行，會互相覆蓋結果，一個指令的 `finally` 也會關掉另一個指令正在用的連線。這台電腦只有一位使用者，同時執行的機會不高，但 UI 會定期呼叫，前一個指令較慢時仍可能重疊。以一把行程內的鎖包住整個 `callAPI`，行程內的競爭就不存在，也不需要另外設計「等鎖期間初始化狀態被別的連線改掉」的檢查。鎖的順序固定為：`callAPI` 鎖 → 卡片鎖。

序列化的副作用：一個指令在等卡片鎖的期間，之後送來的指令都排在它後面，包含 `verifyTS`、`verifySignatureByCert` 這類不碰卡的指令；現行程式沒有這種等待。不碰卡的指令不能直接排除在 `callAPI` 鎖之外，因為它們同樣讀寫 `returnMap` 與資料庫連線這些 static 欄位，這正是要序列化的原因。所以做法是把 HCAAPI 等卡片鎖的上限設短（待決 A），並向前端確認 socket 呼叫的逾時是否長於這個上限加上指令本身的執行時間（待決 O）。

**初始化狀態。** 不再以 Module 與 Session 的 handle 代表「已初始化」，改為一個不可變的物件，內容是使用者代號、操作者代號、PIN、卡號、讀卡機模式。規則：

| 事件 | 初始化狀態 |
|---|---|
| `initialize` 成功 | 整個替換為新的 |
| `initialize` 失敗 | 清除 |
| `closeModule` | 清除 |
| 卡號比對不符 | 清除，回報需重新初始化，不送 PIN |
| 登入回 PIN 類錯誤 | 清除，不重試 |
| `checkHCAAPI` | 不影響（現行程式會關掉已開的 Module，等於作廢初始化；新設計不保留這個副作用，見 §10） |
| `updateCardinfo`、`specialUpdateCardinfo` | 見 §10 待決 |

各指令：

| 指令 | 修改後 |
|---|---|
| `initialize` | 取鎖 → 開 Module → 讀卡號 → 登入驗 PIN → 取公私鑰確認可用 → 關閉 → 放鎖。資料庫查詢移到放鎖之後。成功後建立初始化狀態 |
| `makeSignature` | 見 §6.6 |
| `updateCardinfo`、`specialUpdateCardinfo` | 取鎖 → 開、做、關 → 放鎖 |
| `checkHCAAPI` | 取鎖 → 開 Module、讀卡片資料、關閉 → 放鎖 |
| `closeModule` | 清除初始化狀態。若行程處於「卡片資源異常」則再試一次關閉 |
| `verifySignatureByCert*`、`verifyTS` | 不變 |

**換卡保護**：每個用卡指令都會用記住的 PIN 重新登入。登入前先讀卡號與初始化狀態中的比對，不符就不送 PIN。

**額外成本**：每個用卡指令多一輪開關，約 1 秒。批次簽章整批只多一次。

### 6.6 批次簽章（`makeSignature`）

決議：鎖內取完整批簽章，鎖外才做保存。

| 階段 | 持鎖 | 內容 |
|---|---|---|
| 1 檢查 | 否 | 確認初始化狀態存在；取使用者簽章憑證（`HCAEmrSql.getSigCert` 從資料庫讀，不碰卡，所以可以在鎖外） |
| 2 簽章 | 是 | 開 Module → 比對卡號 → 登入 → 取金鑰 → 逐份：簽章登記鎖定（L）、讀取待簽資料、轉為位元組、`HashFunction`、`MakeSignature` → 關閉 → 放鎖 |
| 3 保存 | 否 | 逐份：時戳查詢、組簽章 XML 並上傳、確認檔案、回寫資料庫、PDF 搬移 |

`HashFunction` 與 `MakeSignature` 都需要 Session，必須在鎖內。時戳查詢、FTP、資料庫回寫都不碰卡。

失敗時的處理：

| 情況 | 處理 |
|---|---|
| 等不到鎖 | 整批未開始，回報「卡片使用中」 |
| 階段 2 第 N 份失敗 | 停止簽章並清理、放鎖。前 N−1 份的簽章已取得，照常進入階段 3 保存；第 N 份起回報失敗。結果與現行逐份處理相同 |
| 階段 3 第 M 份保存失敗 | 停止。前 M−1 份已保存；第 M 份起的簽章只存在記憶體，直接丟棄，使用者重新簽章即可（重簽沒有副作用） |
| 已取得簽章，清理失敗 | 簽章照常進入階段 3；行程依 §6.3 處理資源異常 |

**現行程式每份文件的步驟與成功點**（讀程式所得，未實際執行驗證）：

| 步驟 | 動作 | 用卡 | 寫入的地方 | 中途失敗後 |
|---|---|---|---|---|
| ① | 簽章登記鎖定（狀態 L；由代碼表開關控制是否啟用） | 否 | 資料庫，立即生效 | L 留著；程式沒有把 L 改回的路徑。同一筆之後可以再次登記 L |
| ② | 讀取待簽資料、組文件；PDF 類寫暫存檔 | 否 | 記憶體、`hcatemp\source.pdf` | 可整份重做 |
| ③ | `HashFunction`、`MakeSignature` | **是** | 記憶體 | 可整份重做 |
| ④ | 時戳查詢 | 否 | 記憶體 | 可整份重做 |
| ⑤ | 組簽章 XML 並上傳 | 否 | 檔案伺服器 | 可整份重做，重傳同一路徑 |
| ⑥ | 確認檔案確實在檔案伺服器上 | 否 | 無 | 可整份重做 |
| ⑦ | 回寫工作清單為已簽（`saveSheetWorklist`）與作業紀錄 | 否 | 資料庫 | **成功點**：這一步之後文件即為已簽 |
| ⑧ | PDF 類：刪除原檔、上傳到新位置 | 否 | 檔案伺服器 | 資料庫已指向新位置，但檔案可能沒搬過去 |
| ⑨ | 登記「完成」（狀態 C） | 否 | 資料庫 | L 留著，但文件已是已簽 |

- 程式沒有關閉 JDBC 的自動提交（`src` 內找不到 `setAutoCommit`），推定每一句 SQL 各自提交。`callAPI` 結尾的 `commit` 與例外時的 `rollback` 因此不構成交易，前面幾份文件的寫入不會被後面的失敗撤回。
- 一份文件算「已簽」的時間點是步驟 ⑦。步驟 ⑦ 之前失敗的文件可以整份重做；步驟 ⑦ 之後不應重簽。
- 步驟 ⑧、⑨ 在成功點之後失敗所留下的不一致（檔案未搬、L 未改為 C）是既有行為，不是本設計引入的，也不在本次修正範圍，列在 §8。

簽章登記由代碼表開關控制（`EmrGeneralSheetSignStatus.getOpenRegister`）。開關關閉時步驟 ①、⑨ 不做任何事，沒有 L 與 C，每份文件只剩工作清單一個狀態；待決 H、I 都不適用。現場實際的設定未知（待決 M），驗收要兩種設定各測一次。

L 的作用（讀程式所得）：同一份文件若已有另一筆登記是鎖定或完成，步驟 ① 會把自己那筆改為 Expired 並回報失敗，所以 L 是防止同一份文件被重複簽章的鎖定標記。同一筆登記停在 L 時可以再次鎖定。L 是否也被其他程式用來防止文件內容被修改，未知。

其他已確認的事：程式定義了 Pending、Locked、Completed、Failed、Expired 五種狀態，但 HCAAPI 只寫入 L、C、E，簽章或保存失敗時不寫 Failed，登記就停在 L。重試時以文件、簽章方式、簽章狀態三者找回同一筆登記並再次鎖定，不會新增一筆；所以殘留的 L 不妨礙同一種簽章方式重試，但會讓其他簽章方式的登記在步驟 ① 被改為 Expired。步驟 ① 失敗時現行程式整批在這一份停止；兩階段化之後比照「第 N 份簽章失敗」處理：步驟 ① 是在鎖內做的，此時 Module 開著，所以同樣要停止、關閉 Module、放鎖，前面已取得簽章的文件照常保存。

狀態分屬兩個欄位，彼此獨立：步驟 ①、⑨ 寫的是簽章登記（`emr_general_sheet_sign_status`，鎖定之前 → 鎖定 L → 完成 C），步驟 ⑦ 寫的是工作清單（`emr_general_sheet_worklist` 的簽章狀態，未簽 → 已簽）。因此會出現「工作清單已簽、簽章登記仍停在 L」的組合，就是步驟 ⑦ 成功而 ⑨ 之前失敗的結果。

迴圈內原有的 EEC 上傳不屬於簽章流程，將由另外的實作處理，不列入步驟表，也不在本設計範圍。

**兩階段化之後的一致性規則**：

- 鎖內做步驟 ①②③，鎖外做步驟 ④ 到 ⑨。成功點仍是步驟 ⑦，定義不變。
- 步驟 ③ 取得的簽章在步驟 ⑦ 之前只存在記憶體，任何時候丟棄都沒有副作用。
- 與現況的差異：現況同一時間最多只有一份文件停在「已登記 L、未到成功點」；兩階段化之後，保存階段中止時，同一段內尚未保存的文件都會停在 L。殘留的 L 由誰清理、是否影響下一次簽章，見 §10 待決 H。

**鎖內要放哪些步驟**（待決 I）：只有步驟 ③ 用卡。上面的規則把 ①②③ 都放在鎖內，是為了維持現行「先登記、再讀資料、再簽章」的順序。可以把 ①② 移到取鎖之前以縮短持鎖時間，取捨如下：

| 做法 | 持鎖時間 | 代價 |
|---|---|---|
| ①②③ 都在鎖內 | 最長 | 無 |
| ② 移到取鎖之前，① 留在鎖內 | 省下讀文件與 PDF 取檔的時間 | 順序變成「先讀資料、後登記」。登記失敗的文件，已讀的資料丟棄即可 |
| ①② 都移到取鎖之前 | 最短 | 等不到鎖時，整段文件已經都停在鎖定（L），待決 H 的影響範圍變大 |

尚未定案。先量測各步驟的實際耗時；需要縮短時優先考慮第二種，因為步驟 ② 是鎖內最花時間的非用卡動作，而步驟 ① 留在鎖內可以不擴大待決 H。但第二種把順序改成「先讀資料、後鎖定」：如果 L 也用來防止文件內容被修改，讀完之後、鎖定之前內容可能被改掉，簽到的會是舊內容。要先弄清 L 在其他程式的用途才能採用。

實作前要處理的事：

- 步驟 ⑤ 讀的是 static 的 `HCAUtils.document`，它在步驟 ② 被覆寫；步驟 ②、⑦ 還會讀寫 `chartNo`、`documentSystem`、`subFlag` 等 static 欄位。每份文件的內容、雜湊、簽章與這些欄位要各自保留到保存階段。
- PDF 類文件在步驟 ② 寫入固定檔名的 `hcatemp\source.pdf`（`HCAEmrSql.java:646`），步驟 ⑧ 才上傳。整批先讀再保存會互相覆蓋，需改為每份文件各自的檔名。
- 現行程式有多處針對記憶體不足的防護，且執行環境是 32 位元 JVM。整批文件同時留在記憶體，批次大時可能不足。

為了同時控制記憶體與持鎖時間，階段 2、3 以「分段」為單位執行：每段 K 份，簽完一段、放鎖、保存一段，再取鎖簽下一段。K 等於整批時就是上面的決議；K 的上限見 §10 待決。

持鎖時間估計：每份文件約為讀取待簽資料加雜湊加簽章（簽章實測約 1 秒），整批另加一輪開關約 1 秒。批次超過十餘份時就可能超過 iccard 的 15 秒等待上限，需以實測決定分段大小。

### 6.7 行為對照

| 情境 | 修改前 | 修改後 |
|---|---|---|
| HCAAPI 已 `initialize`、閒置中，iccard 開處方 | 登入失敗 9039 | 立即取得鎖，正常簽章 |
| HCAAPI 正在批次簽章的鎖內階段，iccard 開處方 | 登入失敗 9039 | 等待；超過上限回報卡片使用中 |
| HCAAPI 正在批次簽章的保存階段，iccard 開處方 | 登入失敗 9039 | 立即取得鎖，正常簽章 |
| iccard 簽章中，HCAAPI 執行任何用卡指令 | 9062，或影響 iccard 的 Session | 等待約 3 秒後執行 |
| 一方行程當掉 | 視當下狀態而定 | 鎖自動釋放 |
| 鎖檔無法建立 | 不適用 | 兩邊都拒絕用卡並顯示訊息 |
| 一方關不掉 Module | 無人察覺 | 該方不放鎖並提示重啟；對方逾時並顯示佔用者 |

HCAAPI 對前端的行為差異（指令格式不變，但前端需要知道）：

- PIN 類錯誤與卡號不符，現在可能在 `makeSignature`、`updateCardinfo` 時才回報，不只在 `initialize`。
- 任何用卡指令都可能回報「卡片使用中」。
- `initialize` 之後不再佔著卡；每個用卡指令多約 1 秒。
- `checkHCAAPI` 不再作廢已完成的初始化。
- 批次中途失敗時，「已簽章但未保存」的文件會被丟棄並回報失敗，與現行「逐份簽完立即保存」的中間狀態不同，最後結果相同。

### 6.8 共用元件

用卡流程不在兩個 repo 各寫一份。由 iccard 開發一個共用元件，產出獨立的 jar，HCAAPI 把它放進相依。理由：只有一份實作與一組測試；iccard 有測試與 POC 可以先把它驗證完；HCAAPI 目前沒有測試，直接引用驗證過的元件比就地修改安全。

元件負責的事：鎖（§6.2）、用卡一次的流程與清理（§6.3）、卡號比對、卡片資源狀態與復原。

元件不負責的事：簽什麼、簽幾份、簽完如何保存。這些留在各自的程式裡，以回呼的方式在「已登入」的區段內執行。HCAAPI 的雜湊、批次簽章、讀卡片資料都是這樣接上去的。

限制：

- 只依賴 JDK 8 與廠商 jar。不引用 iccard 的例外類別、設定類別、log 框架或 Spring。log 由呼叫端提供一個簡單的介面。
- 不把廠商 jar 包進去。兩支程式各自提供自己版本的廠商 jar；`HCAAPI` 物件由呼叫端建立後交給元件（iccard 需要先經過 `HcaNativeBootstrap`）。
- 只使用兩個版本的廠商 jar 都有的方法。已比對：HCAAPI 使用的 1,0,10,1208 的公開方法是 iccard 使用的 1,0,12,410 的子集，後者多 7 個方法（`MakeSignatureEx2`、`GetHCACertType`、`InitSOSession`、`UnblockUserPIN`、`VerifySignatureByCert2`、`CryptCertGetSignatureAlgorithm`、`CryptSignatureGetAlgorithm`），元件不得使用。`InitModule`、`InitSession`、`GetHCACardSN`、`GetKeyObjectHandle`、`HashFunction`、`MakeSignature`、`CloseSession`、`CloseModule` 兩版簽名相同。
- 不解讀錯誤碼的業務意義。兩個版本在相同情況下回的錯誤碼不同（9062 與 9039）。元件只認得 PIN 類錯誤碼（9039、9041、9043）以決定不重試，其餘原樣交給呼叫端。

介面草案（名稱待定）：

```java
// 一次用卡期間，呼叫端可以使用的東西
public interface HcaCardSession {
    HCAAPI api();
    int module();
    int session();      // 未登入時為 0
    String cardSn();
}

public interface CardWork<T> {
    T run(HcaCardSession session) throws Exception;
}

public final class HcaCardGate {
    public HcaCardGate(Path lockFile, String ownerName, long waitMillis,
                       Supplier<HCAAPI> apiFactory, HcaCardLog log);

    // 取鎖 → 開 Module → 比對卡號 → 登入 → work → 關閉 → 放鎖
    // expectedCardSn 為 null 表示不比對（第一次驗卡，由 work 讀出卡號並記住）
    public <T> T withLogin(String pin, String expectedCardSn, CardWork<T> work)
            throws HcaCardException;

    // 取鎖 → 開 Module → work → 關閉 → 放鎖；不登入、不送 PIN（checkHCAAPI 用）
    public <T> T withModule(CardWork<T> work) throws HcaCardException;

    public ResourceState state();   // IDLE、IN_USE、FAULTED
    public boolean tryRecover();    // FAULTED 時再試一次關閉
    public void checkLockFile() throws HcaCardException;   // 啟動時檢查
}

public final class HcaCardException extends Exception {
    public enum Reason {
        BUSY,               // 等不到鎖；未呼叫 DLL
        LOCK_UNAVAILABLE,   // 鎖檔無法建立或開啟；未呼叫 DLL
        CARD_MISMATCH,      // 卡號不符；未送 PIN
        LOGIN_FAILED,       // InitSession 回錯誤碼（9039、9041、9043 等）；已清理
        DEVICE_ERROR,       // 其他步驟 DLL 回錯誤碼；已清理
        RESOURCE_FAULTED,   // 本行程先前關不掉 Module
        WORK_FAILED         // work 本身拋例外；已清理
    }
    public Reason reason();
    public int errorCode();     // DLL 的錯誤碼，沒有則為 0
    public String owner();      // BUSY 時的佔用者，可能為 null
}
```

行為要點：

- `work` 正常回傳、但之後關 Module 失敗：`withLogin` 仍回傳 `work` 的結果，不拋例外；狀態變為 `FAULTED`，之後的呼叫拋 `RESOURCE_FAULTED`（先自動 `tryRecover` 一次）。
- `work` 拋例外：照樣完整清理，再以 `WORK_FAILED` 包裝拋出。
- 失敗路徑上關 Module 也失敗：`LOGIN_FAILED`、`CARD_MISMATCH`、`DEVICE_ERROR`、`WORK_FAILED` 之後如果關 Module 也失敗，照樣拋原本的 reason，狀態同時變成 `FAULTED`。`BUSY` 與 `LOCK_UNAVAILABLE` 沒有這個分支，因為那時還沒有開 Module。
- 登入失敗獨立為 `LOGIN_FAILED`，與其他步驟的 `DEVICE_ERROR` 分開。「遇到 9039 就停」與 9043 的處理（§6.4）只在 `LOGIN_FAILED` 時判斷錯誤碼；其他步驟即使回了相同的數字，也不當成 PIN 問題。
- `work` 內不得保留 `session` 物件到回呼之外；回呼結束後 handle 即失效。

交付方式：iccard 的 Gradle 多一個產出（獨立的原始碼集或子專案），jar 帶版號。HCAAPI 引用該 jar。元件的版號寫進 `.owner` 檔，方便現場確認兩邊用的是同一版。

## 7. 相容性與部署

- **混版不保證互斥，也不保證行為無退化。**
  - 只更新 iccard：舊版 HCAAPI 不取鎖，仍然從 `initialize` 握著 Session 到 `closeModule`。這段期間 iccard 一定取得到鎖、卡號也相符，於是送出 PIN 並得到 9039，與現在完全相同。現行 iccard 每次簽章都重新開 Module 並登入（讀程式所得），所以新版不會多送，也不會少送。**iccard 先上版不會消除鎖卡風險。**
  - 只更新 HCAAPI：它不再握著 Session，佔卡的窗口從整段簽章期間縮小為每個指令執行的期間，iccard 得到 9039 的機會減少。不過兩邊仍然沒有互斥：批次簽章在鎖內整段簽完，十餘份就會佔卡十幾秒，這段期間舊版 iccard 不取鎖、照樣登入，重疊時會出現 9039、9062，彼此關 Module 也會讓對方進行中的操作失敗（9016）。窗口多大要量測（§9 第 6 項），並與待決 B 的分段大小一起評估。第二版寫的「相撞的機會比現在多」只算了相撞的次數，沒有分辨哪一種會送 PIN，在此更正。
  - 所以危險來自「HCAAPI 還是舊版」這件事本身，與 iccard 是新是舊無關。見 §8 與待決 J、K。
- **開發順序**（不是上版順序）：
  1. iccard：開發共用元件並改用它。
  2. HCAAPI：先把建置改為 Gradle，原始碼與 `lib/` 的 jar 不動，產出與現在等價。這一步不改行為，單獨驗證。
  3. HCAAPI：引用共用元件，完成 §6.5、§6.6 的修改。
- **上版順序尚未決定**，見待決 K。兩支都更新之後互斥才成立。
- HCAAPI 升級到 Spring Boot 2 是另案，不在本設計範圍，也不是互斥的前提。建議排在第 3 步之後：屆時用卡的部分已抽到共用元件，`HCAUtils` 較容易整理。
- 上線前逐項確認：兩邊使用同一個鎖檔路徑與相同的規則；所有會開 Module 的入口都走共用流程；現場電腦的 `C:\opdsysora\newHis\` 存在且兩支程式的執行帳號都可寫入。
- 兩支程式啟動時就檢查鎖檔可否建立並記錄。否則更新後會因鎖檔失敗而無法簽章。

## 8. 風險與未解問題

| 項目 | 說明 |
|---|---|
| 行程在持卡時當掉 | 鎖會釋放，但卡片是否停在已登入狀態、下一個行程能否正常登入，未驗證。可用一次實驗確認（§9 第 4 項） |
| 批次簽章的記憶體與持鎖時間 | 見 §6.6，需實測後決定分段大小 |
| 輪詢取鎖不保證公平 | iccard 一次開處方只簽一次（`generateQrCodes` 的複數是指 QR Code 影像），單次持鎖約 3 秒。但醫師連續開幾張處方時，iccard 可能在 HCAAPI 兩次輪詢之間又把鎖拿走，讓 HCAAPI 等超過它的上限。這是推論，尚未量測（§9 第 6 項）。若確實發生，依序考慮兩個對策。一、短暫讓出：元件放鎖後，同一行程在短時間內（例如 200 ms）不立刻再取鎖；實作簡單，但只是提高對方拿到的機率。二、排隊鎖：再加一個檔案（例如 `hca-card.queue`），兩邊都先取排隊鎖、再取卡片鎖、拿到卡片鎖後立刻放掉排隊鎖；等待中的一方握著排隊鎖，另一方無法插隊。排隊鎖同樣用作業系統的檔案鎖，行程結束自動釋放，不會留下殘留的登記；兩邊對稱，取鎖順序固定所以不會死結。不採用「在檔案裡寫一筆登記」的做法，因為登記的一方當掉後紀錄會殘留。採用排隊鎖時，等待上限要涵蓋兩把鎖的總時間，卡片資源異常時的逾時訊息仍要顯示佔用者 |
| 第三方程式 | 其他使用同一張卡的程式不遵守這把鎖，仍可能干擾 |
| 關 Module 失敗時的復原 | 設計為不放鎖並提示重啟。這個情況在實驗中沒有出現過，實際的錯誤碼與重試是否有效未知 |
| 9039 是否扣 PIN 次數 | 未知，見 §3.4。廠商元件兩個版本都沒有查詢 PIN 剩餘次數的方法 |
| **HCAAPI 仍是舊版期間的鎖卡風險** | 舊版 HCAAPI 握著 Session 時，iccard 每開一張處方就得到一次 9039；若 9039 會扣次數，連開三張就鎖卡。這個風險今天就存在，而且只要 HCAAPI 還是舊版就不會消失，包含「iccard 已上版、HCAAPI 尚未上版」的整段期間（§7）。對策見待決 J、K、L |
| HCAAPI 批次的既有不一致 | 成功點之後的 PDF 搬移或登記完成若失敗，資料庫與檔案伺服器、簽章狀態會不一致（§6.6 步驟 ⑧、⑨）。既有行為，本次不修 |
| 對業務狀態的影響 | 本設計不改變病歷文件簽章狀態的種類、欄位與成功點（§6.6 步驟 ⑦）。但批次兩階段化會改變時序：同一段內的文件會先全部進入鎖定（L），見待決 H。iccard 這一段沒有寫入任何業務狀態，簽章只用來產生 QR Code 並回傳（已讀 `QrCodeOrchestrator`）。新增的狀態只有行程內的卡片資源狀態與 HCAAPI 的初始化狀態，都不持久化 |
| HCAAPI 的建置轉換 | 目前是 IDE 專案，`deploy/` 內還有 Java Applet 用的網頁。改為 Gradle 時要確認現行的產出有哪些仍在使用，以及 NHI 模式（`HCACSAPIApplet.jar`）不受影響 |
| 共用元件跨版本執行 | 元件對著新版廠商 jar 編譯，在 HCAAPI 的舊版上執行。以測試限制只能使用兩版共有的方法（§9） |
| HCAAPI 修改幅度 | `HCAUtils` 約三千行、全 static、沒有測試。批次兩階段化是其中風險最高的修改 |

## 9. 驗證計畫

1. 鎖類別單元測試：行程內互斥、逾時、鎖檔無法建立時拒絕、釋放後可再取得；以兩個 JVM 驗證跨行程互斥，並交換角色。另測：卡片資源異常時鎖確實還在（另一個 JVM 取不到）；同一個 JVM 在持有鎖時再次取鎖、以及異常狀態下 `tryRecover`，都不會拋出 `OverlappingFileLockException`。
2. 共用元件以假的 DLL 介面測試：
   - `CloseSession` 失敗時仍會呼叫 `CloseModule`。
   - 先回有效簽章再讓 `CloseModule` 失敗：簽章被回傳、只簽一次、鎖沒有釋放、下一次用卡先重試關閉。
   - 操作回錯誤碼時仍完整清理並放鎖。
   - 卡號不符時沒有呼叫 `InitSession`。
3. POC 加入「使用互斥鎖」選項，重跑 [實驗文件](hca-pcsc-experiment.md) 的 E1～E3，預期兩邊都不再出現 9039、9062、9016，且所有簽章驗章通過。
   另加一輪確認 §6.3 的假設：一方登入後不呼叫 `CloseSession`、只呼叫 `CloseModule`，放鎖；另一方取鎖後登入，預期成功。若失敗，「關 Session 失敗、關 Module 成功視為已清理」這條規則要改。
4. 行程中止實驗（一次）：一方握住 Session 後強制結束行程；另一方依序 InitModule、讀卡號（都不需要 PIN）、登入一次。記錄每一步的錯誤碼。登入若回 9039，風險與已做過的三輪相同，不重試。
5. 兩支正式程式實機驗證，使用實際的執行帳號與讀卡機：HCAAPI 已初始化時開處方；批次簽章的鎖內階段與保存階段各開一次處方；兩邊同時操作；`initialize` 後換卡再簽章；批次中途拔卡。簽章登記開關開、關各測一次。
   混版情境（依待決 J）：舊版 HCAAPI 已初始化時，新版 iccard 開處方，預期只送出一次 PIN，之後停止並提示，再開第二張處方不會再送 PIN。
6. 量測：批次簽章每份文件在鎖內的耗時、整批的記憶體用量，用來決定分段大小與等待上限。另量測醫師連續開幾張處方時 HCAAPI 等鎖的時間，確認 HCAAPI 的等待上限夠不夠，以及是否需要放鎖後的短暫讓出。
7. iccard 既有的 `hcaJniIntegrationTest` 與 HCA 相關單元測試通過。
8. 共用元件相容性：以測試檢查元件只引用兩版廠商 jar 共有的方法；並把同一個 jar 掛上 HCAAPI 的舊版廠商 jar，以 POC 實機跑過用卡一次。
9. HCAAPI 改為 Gradle 建置後、引用共用元件前：以現行功能回歸一次（初始化、批次簽章、憑證上傳、驗章，以及 NHI 模式）。

## 11. 考慮過但未採用的做法

| 做法 | 未採用的原因 |
|---|---|
| 鎖住整段 `initialize → closeModule` | 病歷簽章期間完全無法開處方；前端沒送 `closeModule` 時會一直佔著；不同指令由不同執行緒處理，行程內的鎖也無法跨執行緒釋放 |
